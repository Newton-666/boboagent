# Harness 技术层：信号设计纪律（怎么调试细节）

> 状态：定稿 · 2026-08-23 · owner 定（四护栏）· 属于**技术层**（非范式/非宏观）
> 适用场景：所有"信号设计/打分/LLM 动态判断/归档判定"类技术细节——含记忆归档、上下文组成、工具选择的打分。
> 前置事实（owner 经验）：信号设计是**迭代活，一次定不成**；易陷入"反复调试把别的东西弄散"。

---

## 四条护栏

### 护栏一：先定"怎么知道有效"，再定信号本身
设计任何信号前，必须先回答：用什么指标/测试证明它有效？**测不出来的信号不落地**。
第一次信号的目标不是"完美"，是"可测"——拿标注样本验证它能区分对错（如"该进记忆 vs 不该进"）。

### 护栏二：三轮上限，失败即停，停的是设计不是调参
同一信号调三轮仍不合格 → 停止，重新审视**信号设计**（打分维度错了？反馈信号错了？），
不是继续调第 4 轮。**绝不出现"调到第 10 次勉强能用"**。

### 护栏三：信号工作与结构工作分轨
调试信号只碰"信号相关"文件，**不碰走廊/墙/通信结构**——信号调不好时，结构必须原封不动。

### 护栏四：每轮一个实验，独立验证，失败即回退
每轮信号调整 = 一次实验（分支 + 测试 + 基线 diff=0），失败回退到上一版，不留半成品。

## 测试成本纪律（2026-08-24 定，事故教训）

**事故**：真 LLM 多步 A/B 测试（12 次完整运行）烧约 4M token，且日志截断致 A 变体结果缺失——成本失控 + 数据不完整。

**规则**：
1. **验证优先用便宜栈**：基线 diff=0 / 单元测试 / 准确性评估 / mock A/B / 启动冒烟——全部确定性/低成本，够可信；
2. **真 LLM 测试必须预设硬 token 预算**（如 ≤50k/次），超预算立即停；
3. **真 LLM 测试最少样本**（1-2 任务 × 单变体），多步任务的真实成本按 210-565s/2M token/6 任务量级预估后再开；
4. 任何后台测试**必须落盘完整输出**（避免 stdout 截断致数据缺失）；
5. 测试前先算账：这个测试的价值 vs 预估 token 成本，不划算就不跑（护栏二同精神：三轮上限）。
6. **后台测试期间绝不切分支/动工作树**（2026-08-24 事故：合后确认全量跑在 main 上，中途切到 D 分支 → pytest 读实时工作树被污染，结果作废重跑）——后台测试启动后，测试结束前不 checkout、不改文件。
7. **验证脚本必须带硬预算守卫 + 单调用超时**（2026-08-24 二次事故：意图缓存验证脚本无预算守卫，跑 eng.run() 无限重试 30+ 分钟、0 输出）——任何跑真实 LLM/引擎循环的脚本，启动前必须写 BUDGET + 每调用 timeout，超限即杀；能结构验证的不跑真 LLM。

## 流程（每次动手前走完）

1. 白话方案给 owner：信号是什么 / 怎么打分 / 怎么证明有效；
2. owner 点头 → 动手；
3. 三轮上限内出结果；调不出来 → 停下来向 owner 汇报**设计问题**，不在细节打转。
