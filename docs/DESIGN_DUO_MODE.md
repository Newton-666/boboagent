# 设计任务单：/duo 双员制（商讨 + 实现验收）

日期：2026-07-27。状态：已与用户拍板设计，待实现。
前置基建：`tools/spawn_worker.py`（fork-join，worker 用全量工具、同模型配置，
结果经 `read_worker_result` 读取；同一轮可并行派多个 worker）。

---

## 0. 一句话定义

/duo 是**单次任务的执行方式**，不是模式开关。
一个任务用双员方式跑完，自动回到普通状态——没有"进入/退出模式"的状态管理。
中途 Esc / Ctrl+C 打断，和打断普通任务完全一样。

## 1. 两种用法

### 用法 A：商讨（deliberate）

触发：用户说 `/duo 商讨：<问题>`（第一版也可自然语言"用双员商讨一下 xxx"）。

流程（主 Bobo 当中继，worker 之间不直接对话）：

```
主 Bobo ──spawn──→ A：独立出方案（观点 + 理由 + 风险）
主 Bobo ──spawn──→ B：拿到 A 的方案文本，任务书要求"挑刺/反驳/补充"
                     （B 只看到方案，看不到 A 的推理过程，也不必知道来源）
主 Bobo ──汇总──→ 决策清单：
                     · 共识：…
                     · 分歧：A 认为… / B 认为…
                     · 主 Bobo 的建议：…
                     · 待用户拍板：1) 2) 3)
```

设计意图：同一模型也能产生视角差异——角色任务书不同
（"提方案" vs "找毛病"），信息隔离天然制造分歧。
以后想加大差异，把 B 挂到不同 provider 即可（本版不开，见 §4）。

### 用法 B：实现 + 验收（implement & verify）

触发：`/duo <实现类任务>`，例：`/duo 把 diff 触发逻辑重构到 xxx`。

流程：

```
主 Bobo ──spawn──→ A：直接改代码（trash 备份 + git 兜底，沿用现有惯例）
主 Bobo ──spawn──→ B：事后验收。B 的上下文只有：
                       ① 原始需求 ② 改动文件清单 ③ 预先写死的验收标准
                     B 看不到 A 的推理，独立判断：通过 / 打回（附理由）
                     打回 → A 修一轮 → B 复验，最多 2 轮
                     2 轮仍不过 → 升级给用户拍板，不继续空转
```

**硬性规则：验收标准必须预先写进 B 的任务书**（什么是"过"要可判定，
不许写"看看有没有问题"这种开放标准）。

## 2. 信息隔离规则

- B（验收/评审）只能拿到：需求、文件清单、验收标准、（商讨模式下）A 的方案文本。
- B 拿不到：A 的推理过程、工具轨迹、自我评价。
- 目的：避免"看在自己面子上放过自己"——这是双员制存在的全部意义。

## 3. 成本与上限

- token 开销约为单员的 1.5–2x（用户已确认：钱的问题不用管）。
- 打回循环硬上限 2 轮，之后必须升级，禁止无限互踢。
- /duo 任务不嵌套 /duo（worker 里不再派 worker）。

## 4. 明确不做（本版）

- 不做 worker 间消息总线（实时辩论）。商讨用主 Bobo 中继模拟，已够用。
- 不做跨 provider（B 用不同模型是预留扩展口）。
- 不做自动检测触发（"这个任务看起来该用双员"）。第一版只能显式 /duo。
- 不建新工具、不改 spawn_worker 机制。

## 5. 实现形态（关键决定：第一版零新代码）

实现 = **一个 standard.md 技能标准文件**，
路径 `data/skill-standards/duo/standard.md`（仓库内，与 code-fix / git-workflow 同级）。

⚠️ 2026-07-27 更正：录制技能的存储格式已改版（commit 25bbf46）。
旧格式 `skills/*.yaml` + `index.json` 已废弃，新格式为
`data/skill-standards/<name>/standard.md`，头部带
`keywords / excludes / requires` 元信息，正文为"硬约束 + 工作流状态机"风格，
参照 `data/skill-standards/code-fix/standard.md`。duo 必须用这个新格式。

- standard.md 存放在仓库 `data/skill-standards/` 下，随仓库走，
  不存在 `~/.bobo/skills/` 的同步问题（旧坑已随格式改版消失——
  交付时确认 `~/.bobo` 下 bobo 本体与仓库一致即可，沿用既有惯例）。
- 第一版：/duo 不必是真注册的斜杠命令，靠 keywords 匹配自然语言触发即可
  （如 "duo"、"双员"、"两人审"、"商讨一下"、"交叉验收"）。
- 用熟之后若觉得值得，再考虑在 TUI slash 命令里注册真 /duo。

### standard.md 必须包含的内容

- 头部 keywords（duo / 双员 / 商讨 / 交叉验收…）+ status: draft
- 硬约束段：信息隔离规则（§2）、打回上限 2 轮（§3）、禁止 worker 套 worker
- 工作流状态机：商讨三段式（A 提案 → B 挑刺 → 汇总清单）、
  实现验收四段式（A 实现 → B 验收 → 打回循环 ≤2 → 汇总/升级）
- 任务书模板（见下）
- 汇总输出格式（决策清单四段 / 验收结论 通过|打回）

### 剧本必须包含的任务书模板

**A（实现）任务书**：需求原文、允许改的文件范围、trash 备份要求、
完成后自报"改了哪些文件、为什么"。

**B（验收）任务书**：原始需求、改动文件清单、逐条验收标准、
输出格式固定为 `通过` 或 `打回：<理由清单>`。

**商讨 A 任务书**："就 xxx 提出你的方案，给理由和风险。"
**商讨 B 任务书**："有人提出以下方案：<A 的文本>。你的任务是挑刺：
找出假设漏洞、遗漏场景、更优替代。"

## 6. 验收标准（给实现方的考试题）

1. `/duo 商讨：上下文压缩该保 facts 还是保 tool 结果`
   → 输出包含共识/分歧/建议/待拍板四段的决策清单。
2. `/duo 在仓库里新建一个 hello.py 并写一行注释`
   → 有 B 的独立验收结论；文件确实被创建。
3. 人为制造一次打回（验收标准写一条 A 做不到的）
   → 打回 → 修复 → 复验，循环不超过 2 轮后正确升级给用户。
4. 任务结束后继续普通对话，确认无任何"还在双员模式"的残留状态。
5. `data/skill-standards/duo/standard.md` 存在且为新格式
   （头部有 keywords 元信息，非旧 yaml）。
