做了什么

以 duo-A-propose 角色，基于 git log（近 15 次提交集中在 duo 编排器修复）和 README 结构，对 bobo 未来架构提升方向做了系统性提案。

核心观点

Session 应该是骨架，不是隐形概念。 当前架构是"功能平铺"（Memory、Knowledge Base、Skills、Duo、Workers 并列），各模块互不可见——最近 duo 的_briefing() 补丁就是证据。

四个提升方向（按优先级）

#    方向                 优先级        要点
───  ───────────────────  ────────────  ──────────────────────────────────────────────────────────────────────────────────────
1    Session 层落地       高            Session 作为一等架构容器，Context 分热/温/冷三层注入，支持 fork/分支
2    Knowledge Base 进化  中            Session 关闭时自动提取决策写回知识库，条目置信度衰减，冲突检测
3    Worker 2.0           中            资源池管理（并发上限、优先级队列）、Worker 模板、通过 Session Context 而非 Engine 中继
4    Skill 组合引擎       低（探索性）  标准化 I/O、Skill 管道、市场——建议观察 3-6 个月再决定

明确不做

• 多 Agent 聊天室（与 Duo Standard 禁止 A/B 直接通信一致）
    • 插件市场（生态不存在）
    • 全自动 Agent（与"你不需要适应我"哲学冲突）

    需要注意

    • 方向 1 是实现其他所有方向的前提，但 Session Context 须分层管理以防 token 爆炸
    • 知识库自动写回需要人工审核门槛，不能全自动（防污染）
    • Worker 间通信须保持方向性约束，避免死锁▸ 正在派 B 挑刺 …▶️ B 的挑刺原文

    B 的挑刺问题清单

    假设漏洞

    1. "Session 是一等架构容器"的前提未经检验。 当前 Bobo 是单次任务模型（/duo 执行完即结束），persistent session 的使用场景是什么？如果 session    跨对话持久化，和 Knowledge Base 的边界在哪里？——"Session 存短期上下文，KB 存长期知识"听起来干净，但实战中 session 里"还没沉淀的决策"和 KB 里"上次    session 写入的决策"高度重叠。

    2. Fork/分支 session 解决了谁的问题？ Bobo 是单人 agent，fork 会话路径的用例极其模糊——除非用户在同一个问题上有两条互斥探索线并在最后合并，但这更像    git workflow 而非对话 agent 的使用模式。这个功能可能永远不会被触发。

    3. 方向 1 是"前提"的因果链不成立。 Worker 资源池、优先级队列、模板系统完全可以在现有架构上独立实现，不依赖 Session Context 三层注入。把方向 1    绑成所有方向的前置条件，等于把轻量改进绑架成了重量重构。

    4. Hot/Warm/Cold 三层是空壳定义。 方案没说每层的数据类型、大小上限、刷新策略。如果 Hot 包含当前对话 + 项目代码 + 记忆，token 立即爆炸；如果 Hot    太窄，又退化成了现在的 context 参数。没有量化边界的三层分类比不分层更危险——给人一种"已解决"的安全感而实际上什么都没解决。

    5. "自动提取决策写回 KB"的准确率假设过于乐观。 LLM 区分"用户随口一说"和"真正的决策"的准确率远不到可信任的水平。人工审核门槛 = 每次 session    结束弹一个审核列表——用户很快会疲劳，要么全点确认（污染 KB），要么全忽略（功能白做）。

    遗漏场景

    6. 完全没有向后兼容和迁移路径。 现有 Memory、KB、Skills、Duo、Workers 五模块在一个"Session    一等架构"下如何重新挂载？是一次性重构还是渐进迁移？不合入方案就列"高优先级"，等于画了蓝图不给施工图。

    7. Session 的存储和持久化策略缺失。 Session 存内存还是磁盘？Bobo 重启后 session    是否恢复？跨设备同步？这些问题不回答，"一等架构容器"这个说法就落不了地。

    8. 性能/成本模型完全空白。 Hot Context 每次 API 调用都注入，如果 Hot Context 膨胀到几千 token，每次对话的 token 消耗会成倍增加。Kimi 1M    上下文不怕，但换模型呢？没有成本估算的架构提案是 incomplete 的。

    共识

    • 当前架构“功能平铺”导致模块间信息传递脆弱，duo 的补丁已验证这一问题，需要提升模块间的互见性和协作能力。
    • Knowledge Base 的进化方向有价值，但自动写回机制需要防污染设计，人工审核门槛是必要但可能引起疲劳的环节。
    • Worker 的资源池管理、优先级队列等能力可以独立演进，不必须依赖架构级重构。
    • 多 Agent 聊天室、插件市场、全自动 Agent 不做，方向 4（Skill 组合引擎）当前更适合观察而非作为正式提升方向。

    分歧

    • A 认为：Session 应升级为一等架构容器，并作为其他方向的前置条件，通过 Hot/Warm/Cold 三层 Context 注入解决模块互不可见问题。

      B 认为：Session 一等架构的前提未经检验，persistent session 的用例模糊，与 Knowledge Base 边界重叠；统一 Context    协议是更轻量、风险更低的替代方案，且 Worker 资源池等改进无需依赖 Session 重构。

    • A 认为：Fork/分支 Session 是未来探索性能力，可作为架构灵活性的一环。

      B 认为：Bobo 是单人 agent，fork/分支的用例极其模糊，可能永远不会被触发，不应列入高优先级方向的依赖设计中。

    • A 认为：Hot/Warm/Cold 三层分层是解决 token 爆炸的方向性指引。

      B 认为：三层定义缺乏量化边界（数据类型、大小上限、刷新策略），空壳定义可能带来虚假安全感，且未考虑性能成本和模型切换的 token 消耗。

    • A 认为：Worker 通过 Session Context 通信可减少 Engine 中继。

      B 认为：这与 Duo Standard 的信息隔离原则矛盾——B 不应拿到 A 的推理，若 Worker 共享 Session Context，隔离如何保证未说明。

    • A 认为：知识库置信度衰减是避免信息陈旧的有效机制。

      B 认为：需区分“会过时的知识”和“不会过时的知识”，一刀切衰减会让稳定偏好被错误降权，应引入知识类型标签。

    • A 认为：方向 1 是高优先级，是实现其他方向的前提。

      B 认为：方向 1 是重量重构，把轻量改进绑架了，且最近 15 次提交暴露的问题是 duo 编排器内部信息传递脆弱，更直接的方案是强化 duo    的契约，而非动全架构。

    建议

    • 优先采纳 B 的轻量替代方案：为各模块定义统一的 get_context_for(task_type) 接口，由 Engine    在任务启动时组装上下文，快速解决“模块互不可见”问题，避免过早引入持久化 Session 层带来的复杂度。
    • 将 Session    一等架构的方向降级为“探索性方向”，明确其使用场景（如跨对话项目协作、长周期任务）并做出原型验证后，再决策是否上升为高优先级重构。需回答：persistent    session 与 Knowledge Base 的明确边界、Hot Context 的 token 预算上限、重启/跨设备持久化策略。
    • 若后续启动 Session 层设计，必须补充量化定义（每层数据内容、大小 cap、刷新策略）和成本模型（不同模型下的 token 消耗估算），避免空壳架构。
    • Worker 资源池、优先级队列、模板等功能在现有架构上解耦实现，模板优先采用“配置预设 + 可复用的实例参数”，避免与 Session Context    通信的设计冲突；同时必须在提案中明确与 Duo Standard 信息隔离的兼容性方案。
    • 知识库自动写回暂不追求全自动，改为“会话摘要 + 用户确认”的半自动流程，并引入知识类型标签（稳定偏好 vs    时效性知识），为不同类型配置不同的衰减或不变策略，防止污染。
    • 将方向 4 移出正式提升方向清单，列为“观察项”，并设定 3-6 个月后的评审触发条件（如用户主动请求 Skill 串联的频率、社区反馈等）。
    • 短期聚焦解决 duo 编排器信息传递脆弱的根因：强化 duo 内部契约，规范 _briefing() 的生成与校验规则，补全异常路径处理，这比架构重构更符合近期 15    次提交暴露的痛点。
