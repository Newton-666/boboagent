## 一、三视角结论对比

| 视角 | 核心结论 | 关键洞察 |
|---|---|---|
| **RL 方法论** | 可行，但必须防"自举崩溃" | 策略/评估/经验同源 → 收敛到"自信地学错"且不可察觉；**奖励信号必须至少有一个独立锚点**（人工确认 / 确定性代码校验 / 冻结第三方评分器） |
| **Hermes 落地** | 先 A 后 B | A（失败轨迹提炼）有客观成败信号可验证；B（self-evolving prompt）信号弱、需 A 的教训体系做闸门；第一步=失败轨迹结构化归因 + 人工闸门 |
| **批判** | 缩小做 | 判分器/归因不可靠（噪声上建规则）、频率≠因果、prompt 演化毁缓存、自改提示词=权限提升面、维护负担反增；只保留"人审建议流水线 + 版本管理" |

## 二、三视角共识（可以当设计原则）

1. **人审闸门**：LLM/Agent 无直接写权限——只产"建议 patch"，落地必须人审（批判：自改目标函数=权限提升；RL：评估者与策略同源不自证）
2. **数据地基先于自动化**：判分可靠 + 归因结构化，先积累人工标注样本，再谈自动提炼
3. **保守更新门槛**：同模式失败 **≥3 次（须来自不同会话）** 才固化规则；高奖励成功 ≥3 次才抽象技能（三视角不约而同给出 3 次门槛）
4. **缓存红线**：prompt/规则演化必须低频 + 分层注入 + dry-run 验证（不破坏 COST-2 战果）
5. **EVAL 回归验证**：更新先跑回归集，旧能力退化即丢弃，规则可单独禁用/回滚

## 三、bobo 的独特优势（RL 视角最大坑，bobo 天然避开了）

**自举崩溃的前提是"评估器与策略同源"——bobo 的 EVAL 是确定性判分**（文件内容断言/命令输出断言，非模型自评）。这意味着 bobo 的奖励信号**天然有独立锚点**：
- EVAL 判分器 = 确定性代码（独立于 LLM 策略）✅
- 教训册/终审 = 人工锚点 ✅
- 记忆信号衰减 = 结构化规则 ✅

**结论：bobo 是少数"可以安全做自净化"的本地 agent 架构**——RL 理论最大的失败模式在 bobo 这里被确定性 EVAL 天然挡住。这是本讨论最重要的发现。

## 四、批判点回应（每条给缓解）

| 批判 | 严重度 | 缓解（已被共识覆盖） |
|---|---|---|
| 判分器不可靠 | 高 | 确定性判分（非 LLM 自评）+ 判分器自身单测 + 人工抽样复核 |
| 偶然当规律 | 高 | ≥3 次不同会话门槛 + 独立 held-out 集复现 + 阈值可调按季校准 |
| 缓存破坏 | 高 | 低频更新 + 分层注入（evolved 走尾部动态块）+ dry-run 对比 |
| 自我修改失控 | 高 | 只产建议 patch + 人审落地 + base 只读 + EVAL 熔断回滚 |
| 维护负担反增 | 中 | 规则数量硬上限 + 定期淘汰 + 每版强制 diff 与来源轨迹 ID |
| 收益存疑 | 中 | 先离线 A/B 证明收益为正再自动化（P1 阶段做） |

## 五、裁决：落地路径（阶段化，每阶段独立票）

```
P0 数据地基（先做，低成本高杠杆）
  EVAL 失败轨迹加"结构化归因字段"（失败模式：工具/检索/措辞/时机）
  + 判分器单测 + 归因人工标注样本积累
  → 产出：可用的归因数据（自净化系统的"训练集"）

P1 半自动建议流水线（人审闸门）
  失败/成功轨迹 → 自动提炼"候选规则/技能建议"（带来源轨迹 ID + 置信度）
  → 进候选池（不自动落地）→ 人审确认后进规则库/技能标准
  → 产出：自净化闭环的第一版（人审版），验证收益（离线 A/B）

P2 低频自动固化（带全部闸门，B 阶段）
  self-evolving prompt：base 只读 + user 自定义 + evolved 追加段
  + 重置/版本回滚 + 低频触发（≥3 次同类偏好） + 预算上限
  → 与 P1 的教训体系联动（evolved 提炼复用 P1 的质量闸门）
```

**顺序依据**（Hermes 落地视角）：P0→P1→P2，A（规则/技能提炼）先于 B（prompt 演化）——B 依赖 A 的教训体系做质量闸门。

## 六、与现有体系衔接

- EVAL 考场 → P0 归因字段（现状：确定性判分已有，缺归因）
- 教训册 L1-L15 → P1 候选规则的去处（现状：人工提炼，缺自动化）
- 技能标准自动发现 → P1 技能建议的去处
- 票据/回滚制度 → P2 版本管理的机制（现状已有，直接复用）
- COST-2 尾部动态块 → P1/P2 注入通道（evolved 走尾部，缓存红线守住）

## 八、owner 核心论点补录（2026-08-18 第二轮讨论，与 Hermes 聊前必读）

> 这轮是方向校准：从"三视角方法论"收敛到"owner 对自进化的本质定义"。

### 8.1 记忆 ≠ 自进化（owner 原话要义）

- 记忆是**被动的**：只是存储更多、调用时可追溯，但"记忆再多，对自进化本身也没有直接帮助"；
- **自进化的直接载体 = system prompts / rules 文档**（每次组装都注入、直接塑造行为的主动层）；
- bobo 现有 rules 文档体系（不止一个）：`docs/SELF.md`（母文档）、`docs/GUIDANCE.md`、
  `docs/GUI-LESSONS.md`（教训册 L1-L15）、`data/skill-standards/`（11 个技能标准）——
  这些都是"主动层"，自进化要落在它们身上。

### 8.2 必须主动 + 自动 + 后台（不需要用户审批）

- "强化学习的目的，都是让 Agent 具备**主动做出调整**的能力"；
- **不需要用户审批**：审批只用于"执行任务"；自进化是**系统后台自己做的 RL**（类似训练，
  不是任务执行）；
- 最终体验："Agent 越来越了解我的风格、越来越贴近我、像私人秘书、有契约感"；
- 命名愿景："**Agent 有灵魂**"——Hermes 的自进化系统与我们不同，正因不同会达成不同结果；
- 目标：**越来越符合用户使用习惯**，而不只是能力强（所有 Agent 都强）。

### 8.3 固定 token 预算 = 自进化的"活动空间"（owner 关键约束）

- 给 evolved 层设**最大长度**（如 ≤800 tokens），自进化只能在这个空间内"修修补补"；
- 每次用户做新的事 → 微调 prompt：**删一条 / 增一条 / 改一条 / 插入一条**；
- 满额 → 淘汰最旧的/最不相关的（逼系统"记住最重要的，忘掉次要的"）；
- 这同时解决批判视角的"prompt 无限膨胀"。

### 8.4 内化判据（自进化的试金石，owner 原话要义）

- 真正的学习 = **行为直接改变，不需要额外查询**（"不需要额外调用一个新东西就能直接执行"）；
- 如果 bobo 每次执行代码前还要"看一下以前犯过哪些错误"→ **它没学会**（查询式 = 被动）；
- 对应技术：**注入式**（规则在 system prompt/尾部动态块，每次组装自动进上下文）=
  内化 = 下意识；**查询式**（规则在记忆/文件，要主动调工具读）= 被动；
- **关键洞察**：bobo 的注入体系（常驻 prompt + COST-2 尾部动态块）**已经是"内化"的管道**
  ——自进化 = 自动改写注入层的内容，bobo 行为自动跟着变，机制零新建。

### 8.5 信号采集：交给 LLM 判断 + guidance（owner 认可）

- 信号判据（guidance，给 LLM 的收纳标准）：
  ① 用户说"以后/下次/从今往后" + 期望行为 → **工作流模式信号**；
  ② 用户说"不要/别/别用" + 不喜欢行为 → **负强化信号**；
  ③ 用户重复要求同类事 ≥N 次 → **隐含偏好信号**；
  ④ 用户明确说"记住/以后都这样" → **强信号**；
  其余不算信号（普通对话不收纳）。

### 8.6 分级/分文档设计（不自造体系，基于已有文档）

| 层 | 文档 | 作用 | 自进化权限 |
|---|---|---|---|
| 宪法层（永久不变） | 基座 prompt + SELF.md | 身份/边界/执法 | 🚫 永不自动改（防自我放大底线） |
| 行为层（低频） | GUIDANCE.md + 纪律段 | 工作流习惯/通用纪律 | ✅ 可微调（≤N 次/月） |
| 技能层（中频） | skill-standards/ 11 个 | 任务模式 | ✅ 可增删改（带置信度） |
| 偏好层（高频） | **evolved.md（新建）** | 用户个性化 | ✅ 高频微调（预算内删增改） |

- 宪法层只读 = 安全底线（自进化永不碰它，挡住"自我放大"）；
- 每层独立预算 + 独立版本可回滚；
- 作用域三档：全局（GUIDANCE/evolved）/ 会话级（GUI-F24 Request 已有）/ 场景级
  （技能标准关键词触发）——对应 bobo 已有三种注入通道。

### 8.7 节奏决定（owner 拍板）

**不着急执行**：先想清楚、和 Hermes 多聊几轮（把 evolved 淘汰策略、信号采集频控、
宪法层边界等细节磨厚），等整个东西丰富得差不多再执行。当前仅存档讨论，不开票。

## 九、Hermes 批判性分析（2026-08-18 应 owner 要求补录）

> 署名：Hermes（Nous Research）——独立架构师视角，非三视角之一。
> 定位：对全文（含 owner 核心论点）的批判性审阅。不恭维，直接指出站不住或危险的地方。

### 9.1 总判断

**方向成立，论证有一个隐蔽的自洽漏洞。** 最大风险不是文档已防住的"任务层面自举崩溃"，而是**偏好层面自举**——而文档用"确定性 EVAL"论证的整体安全性恰好不覆盖它。

### 9.2 可行性：安全论证只保护了一半

- 第三节的核心论证："EVAL 是确定性判分 → 奖励信号有独立锚点 → 自举崩溃被天然挡住"。
- **该论证只覆盖任务成败信号**（文件断言/命令输出断言）。
- 8.5 的偏好信号是 **LLM 判定 + guidance——无独立锚点**，恰是自举崩溃重灾区：

```
LLM 判断"用户想要 X" → 写入 evolved → 行为改变 → 用户沉默（未察觉）
→ 系统把沉默当认可 → 强化 X → 用户某天发现"Bobo 怎么变成这样了"
```

- 任务失败的自举有确定性判分兜底；**偏好错误无任何兜底**。
- 8.4"内化判据"放大此问题：错误偏好一旦注入即"下意识"，永不再经查询验证。

### 9.3 遗漏点（六项）

1. **淘汰策略只定义预算，未定义判据**（8.3）
   - "最旧"与"最不相关"是两个可能冲突的维度：旧规则可能仍高相关（核心工作流），新规则可能已被覆盖。
   - "最不相关"由谁判？又是 LLM——淘汰环节再引入一次无锚点判断。
   - 未提振荡问题：淘汰后用户回到旧模式，系统是否重学？学回又淘汰 = 震荡。

2. **信号可靠性：guidance 四条全是主观推断**（8.5）
   - "以后/下次"可能是客套；"不要"可能只是这一次不适用；"重复 ≥N 次"可能是用户被迫重复（恰是 Bobo 没学会的信号）。
   - 缓解措施（≥3 次、held-out 复现）只降偶然性，不降系统性误判——LLM 对用户偏好的推断本身有偏差。

3. **宪法层边界是约定，不是机制**（8.6）
   - 谁决定一条规则属于行为层还是宪法层？边界靠文档划分，非代码强制。
   - 人工把规则从 GUIDANCE 提升到 SELF（合理操作）后，"宪法层只读"依赖人的记忆。
   - 需"宪法层变更必须显式双人/owner 确认"的机制，文档未提。

4. **缓存影响：假设了结论，未实测**（共识 4 vs 8.3）
   - "高频微调"与"缓存红线"直接冲突：尾部动态块若在缓存前缀内，每次改动 = 全前缀失效；若在前缀外，是否影响整体哈希取决于实现。
   - **必须 dry-run 实测**，不能假设"尾部 = 安全"。COST-2 是 money。

5. **失败回滚：有版本回滚，无行为级回滚**（共识 5）
   - evolved 里 5 条规则坏 1 条：回滚整版（连带丢 4 条好的）还是单条？未定义。
   - 更隐蔽：**EVAL 只能测能力退化，测不了体验退化**——一条规则可让全部 EVAL 通过但让回复风格令用户反感。整个安全论证建立在 EVAL 上，而 EVAL 有盲区。

6. **用户感知：几乎完全缺失**（8.2）
   - "无审批后台自动"下，用户如何感知自进化发生？感知为"Bobo 变了但不知道为什么"（困惑）或"昨天还这样今天不这样"（不稳定）。
   - "有灵魂"愿景需要"灵魂可解释"：至少 evolved 变更后给轻量可见提示（"我把 X 记住了，以后 Y 场景会 Z"），让用户可纠正。
   - **主流实践（Claude Code 等）全部保留"变更可见"；"无审批后台自动"是唯一把变更藏起来的设计——不是特色，是风险。**

### 9.4 对比其他实践

- 三类主流：① 用户手动编辑 rules（Cursor）；② 自动记忆但查询式（Mem0 / Claude Code 自动记忆）；③ 训练期改权重（RLHF/RLVR）。
- **bobo 想做第四类：运行时自动改写注入层——最激进，确实独特。**
- 最接近参照：Hermes skill 系统（固化经验 + curator 淘汰 + pin 保护），但 Hermes 选查询式（skill_view 加载），与 owner 8.4 的"注入式 = 内化"根本分歧。
- 隐患：同时踩三个地雷——RL 奖励黑客（部分挡住）、工程可维护性（4 层文档 = 复杂度）、用户信任（完全未处理）。

### 9.5 可执行性

- **第一步应比 P0 更小**：先做**信号采集纯日志化**（guidance 四条只记录不动作，跑两周看信号密度与质量）。信号多为误报 → 前提重估；信号质量高 → 再做归因 schema。成本最低的证伪实验。
- **该砍**：P2 完全自动固化（降级为"建议 + 一键应用"）；8.2"不需要用户审批"（保留"变更可见 + 一键撤销 + 变更日志"）；evolved"高频微调"（降频 ≤N 次/月，与缓存红线和解）。
- **该简化**：四级文档分层 → 先只做 evolved.md 一层，宪法/行为/技能靠人工维护。"不自造体系"的声明与 8.6 实际造出 4 层新体系自相矛盾。

### 9.6 结论

**缩小做**：保留 P0 + P1 简化版（人审建议流水线，只收工作流级信号，≥3 次门槛，变更可见可回滚），**P2 与"无审批自动"在 P1 的离线 A/B 证明收益为正之前不开**。

一句话理由：方向对（agent 应学会用户偏好），但当前设计有**两个未裁决的根本矛盾**（人审 vs 无审批；高频微调 vs 缓存红线）、**一个致命盲区**（偏好信号无独立锚点，恰是自举崩溃最隐蔽的形态，而文档安全论证不覆盖它）、**一个信任真空**（用户感知）。

建议讨论方向从"怎么让系统自动改自己"转向"**怎么让用户信任系统改自己**"——后者才是本项目真正没想清楚的部分。

## 十、owner 对"信任真空"的落地回应：用户可见层设计（2026-08-18）

> 这一节是 owner 针对 Hermes 9.3-6"用户感知缺失/信任真空"批判的具体设计，直接补上可见性与可撤销性。

### 10.1 设置内 Self-Evolving 管理模块

- 设置中新增专门的 **Self-Evolving 区块**，管理整个 self-evolving system；
- 显示内容：
  - evolved 层**当前内容**（prompts 被改成什么样）；
  - **变更历史**：每次 RL 修改的记录（时间 / 变更内容 / 来源信号）；
- 每条变更记录配 **回滚按钮**（一键撤销该次修改）——可见性 + 可撤销性闭环。

### 10.2 diff 方式展示 RL 修改（复用现有 diffBlock 组件）

- 变更展示用**与使用中完全同款的红绿 diff**：
  - 新增段 → 绿色高亮；
  - 删减段 → 红色高亮；
- **零新机制**：直接复用桌面端现有 diff 渲染（GUIDE-F3/F8 diffBlock），
  owner 原话："这个 mode 和我们在使用当中的那个 diff 是一模一样的"。

### 10.3 会话内即时通知

- RL 在会话中触发学习完成时 → 像"session deleted"一样**顶部滑入 toast**，
  提示 **"self evolved"**（用户即时感知：Bobo 刚才学习了什么）；
- 与现有 toast 机制（session deleted 滑入）同款，零新交互模式；
- 可点击展开/跳转设置模块查看本次 diff。

### 10.4 设计要点

- **信任三件套**：可见（diff + 变更日志）+ 可撤（回滚按钮）+ 即时感知
  （会话内 toast）——直接回应 Hermes 9.3-6 与 owner"信任不对称"讨论
  （好变化建立信任慢，坏变化摧毁信任快 → 必须"犯错可发现、可纠正、会承认"）；
- **RL 机制与可见层同构**：变更历史 = 版本管理 = 可回溯（与票据/回滚制度同构）；
- 未定决策：toast 出现频率（每次学习都弹 vs 批量汇总）——待 P1 信号日志化
  实验后按实际触发频率定。
## 十一、Hermes 对第十节（可见层设计）的批判性评审（2026-08-18 应 owner 要求补录）

> 署名：Hermes（Nous Research）——对 owner 第十节"信任真空落地设计"的逐条评审。
> 定位：批判性。不恭维。指出仍然站不住或未闭合的地方。

### 11.1 总判断

**第十节解决了"可见/可撤/即时感知"这一半，没解决"看得懂/可验证/沉默≠认可"那一半。**
把"信任"从"完全缺失"推进到"事后可查"——必要，但"事后可查"不是"事前可信"。

### 11.2 信任真空：解决了一半

**已解决**：
- 可见性闭环（diff + 变更历史）✅
- 可撤销闭环（回滚按钮）✅
- 即时感知（会话内 toast）✅

**未覆盖**：
1. **看得懂 ≠ 看得见**：diff 展示的是 prompt 文本（内部语言），Bobo 目标用户
   （B站创作者/播客主）理解不了"在工作流模式信号触发时优先使用 spawn_worker"。
   信任建立在"看得懂"上。需双层展示：自然语言摘要（"Bobo 学会了：X"）为主，
   原始 diff 折叠为高级选项。
2. **来源信号不可验证**：变更历史的"来源信号"是字段名，不是证据。用户看到
   "已学习：用户偏好中文"但自己不记得说过 → 怀疑 Bobo 编造。来源必须带原始
   对话摘录（"你说'以后都用中文写' → 已学习"）。
3. **沉默 ≠ 认可依然成立**（9.2 自举链条）：用户没回滚 ≠ 认可，只是没注意。
   真正语义需显式信号：每次学习给"确认/忽略"而非"回滚/不回滚"（默认忽略，
   不是默认接受）。

### 11.3 可见层设计本身的新问题

**a. toast 会变成骚扰源——且与 owner 自己的"私人秘书"愿景冲突**
- 8.6 偏好层 = 高频微调 × 10.4 toast 频率未定 = 高频打断。
- 8.2 愿景是"私人秘书、契约感"——秘书不会每次学会习惯就通知你。
  **"每次学习都弹 toast"与"越来越像私人秘书"是两种相反的体验叙事。**
- 文案零信息量："self evolved"对用户无意义。要么带具体内容，要么别弹。
- 建议：toast 分级——强信号（明确说"记住"）才弹；弱信号只进设置日志；
  行为级大改弹；词条级微调不弹。默认静默记录，特殊时刻才主动。

**b. diff 对非技术用户不友好（承接 11.2-1）**
- 除"看不懂"外：**diff 公开 prompt 原文 = 把护栏/防滥用层暴露给用户**。
  用户看到防循环规则/护栏措辞会质疑"你为什么要这样设置"，或感到被操纵。
  展示应只覆盖"行为承诺层"，不覆盖"护栏层"。

**c. 回滚按钮的致命缺陷：没处理"学回来"（振荡）**
- 用户回滚"用中文回复"，但信号日志仍记着"用户偏好中文"（用户确实说过）
  → 下次信号触发 RL 又学回来 → 用户再回滚 → 死循环。
- **回滚必须同时降权/删除对应信号源**，否则回滚无效，且用户觉得"Bobo 听不懂人话"。
- 回滚粒度未定义：一次学习批次改 3 条，撤 1 条留 2 条——整批做不到，单条可能破坏依赖。

### 11.4 内化判据 vs 变更可见：不冲突，但体验叙事打架

- 内化判据 = Bobo 的**存储机制**（注入式 vs 查询式）；变更可见 = 用户的**知情权**
  （可见 vs 隐藏）。正交：规则注入式存储（下意识执行）+ 设置留人类可读日志（可查）。
- 但"内化 = 下意识"与"每次变更都弹 toast"在体验上打架。可见层应**低频、安静、
  默认藏在设置里**——存在意义是"用户想查的时候查得到"，不是"每次变化都推给用户"。

### 11.5 整体重新评估

**结论：部分变了，没根本变——P2 依然不该现在开，但开放条件可明确化。**

P2 仍依赖（第十节未解决的）：
- 偏好信号无独立锚点（9.2）——回滚是事后纠正，不是事前锚点；学错 3 天才被发现。
- 缓存红线——第十节零提及，纯 UI 层不触及。
- 信号可靠性——P0 日志化未做，toast 频率都定不下来（10.4 自认）。

**P2 开放条件（6 条）**：
1. P0 信号日志化实验证明信号质量（误报率低于阈值）
2. P1 离线 A/B 证明收益为正
3. 可见层落地（第十节）
4. **新增：回滚带信号源降权**（防振荡）
5. **新增：toast 分级**（强信号才弹，弱信号静默）
6. 缓存实测：尾部动态块改动是否破坏前缀

### 11.6 两个根本矛盾：第十节解决了吗

- **矛盾一（人审 vs 无审批）：部分缓解，未裁决。**
  "无审批 + 事后可撤"是妥协不是裁决；错误窗口期依旧；沉默当认可依旧。
  真正裁决二选一：关键变更事前审批（P1 人审闸门），或显式确认信号
  （学习必须"确认/忽略"，不能静默默认接受）。
- **矛盾二（高频微调 vs 缓存红线）：完全没解决。**
  第十节零提及，原封未动。可见层给人"问题在解决"的错觉，实际上 money 问题没碰。

### 11.7 总结论

**第十节解决了部分信任真空（可见 + 可撤 + 即时感知——把"系统偷偷改自己"变成
"系统改自己但留痕可查"），但没解决：看得懂（diff 对非技术用户是内部语言）、
信号可验证（来源无摘录）、沉默≠认可（无显式确认信号）、回滚防振荡（无信号源
降权）、缓存红线（零提及）。**

"回滚带信号源降权"和"toast 分级"是第十节设计里必须补的两个洞——否则这个可见层
要么无效（学回来死循环），要么变成新的骚扰源（高频弹 toast 杀死秘书感）。

## 十二、两个方向的结构化分析（2026-08-18 owner 提出："RL 机制怎么规划" + "用户如何信任 RL 结果"）

> 这一节是 owner 在第十一节之后提出的两个讨论方向：一边是"强化学习的 model 怎么
> 规划、机制是什么"，另一边是"用户信任 RL 结果（学坏了怎么办）"。

### 12.1 方向一：RL 机制怎么规划（model 设计）

bobo 的"强化学习"是**行为层策略搜索**（非梯度，近似进化策略）。机制要素：

| RL 要素 | bobo 对应 | 设计要点 |
|---|---|---|
| 状态 | 会话上下文 + 用户特征 | 何时触发评估 |
| **动作空间** | evolved 的增/删/改一条 | **有界**（固定 token 预算内） |
| **奖励信号** | 任务成败（EVAL）+ 用户反馈 | **分层**（见下） |
| 策略 | 修改决策规则（何时改/改什么） | 低置信探索 / 高置信利用 |
| 评估协议 | 修改后观察窗口 | **前后对比**，不是自评 |

**奖励信号分层（关键设计）**：
- **硬信号**：EVAL 判分（能力维度，有独立锚点 ✅）
- **软信号**：显式（点赞/纠正/明确说"这样好"）+ 隐式（是否重试/打断/回复被采纳）
- **用户沉默**：⚠️ 最难的信号——**沉默 ≠ 认可**（Hermes 9.2 核心批判），不能当正奖励

**评估协议**：修改一条 → 观察 N 轮 → 硬信号不退化 + 软信号正向/中性 → 接受；
退化/负向 → 回滚。注意 **EVAL 盲区**（体验退化测不出——Hermes 9.3-5）。

### 12.2 方向二：用户信任（RL 结果可信 + 变差时保护信任）

**信任不对称**：好的变化建立信任慢，坏的变化摧毁信任快。设计核心不是"永远不
犯错"，而是"犯错可发现、可纠正、会承认"：

1. **可见性**：变更可见 + 变更日志（Hermes 已提）
2. **可撤销性**：一键撤销 + 版本回滚（用户有"后悔药"）
3. **渐进授权**（关键）：**信任是挣来的，不是给的**——低风险偏好（语言/格式）
   自动学；高风险（行为/权限）先建议、用户确认才应用。系统从"用户确认/忽略"
   的行为里**学习用户的授权边界**（元学习：学用户信任什么）
4. **失败保护 + 诚实**：RL 变差时——检测 + 自动回滚 + **诚实告知**（"我调整了 X，
   发现效果不好，已恢复"）——诚实本身就是修复信任的机制
5. **信任显示**：让用户看到学习效果（"我注意到你偏好中文，已应用"）——正面
   反馈建立信任

**与自动驾驶信任问题同构**：透明 + 可控 + 可问责——不追求"永不犯错"，追求
"犯错可发现、可纠正、会承认"。

### 12.3 两个方向交汇的核心决策点

1. **用户沉默的处理**：建议**低风险自动 + 高风险确认**的渐进授权——用户沉默只对
   低风险偏好生效（沉默 ≈ 无所谓），高风险永远要显式确认（待 owner 拍板）
2. **RL 第一步落地**：Hermes 建议先"信号纯日志化"（只记录不动作，跑两周看信号
   质量）——最低成本的证伪实验（owner 倾向待定）

## 十四、自进化的本质：系统打通 + 用户模型（2026-08-18 owner 核心阐述）

> 这一节是 owner 对自进化系统"是什么"的定性——不是加一个功能模块，而是整个
> agent 运作逻辑的重构。

### 14.1 自进化不是功能，是整个 agent 的逻辑（owner 原话要义）

- "自进化系统不是一拍即合就能完成的，牵扯到 bobo 系统好多模块都需要调整"；
- "自进化不是一个功能，而是整个 agent 的逻辑"；
- **自进化 = Agent 能够不断主动地了解用户意图**——这是贯穿所有模块的运作方式，
  不是某个开关/面板/模块。

### 14.2 系统必须打通，不能是独立模块（owner 核心观点）

- 现状问题：记忆是记忆、Obsidian 是 Obsidian、library 是 library、docs 是 docs、
  prompt 是 prompt——**各自独立、互相封闭**；
- 拆模块是为了**解耦可维护**（防止连锁断裂），但**模块之间不能封闭**；
- **没有任何 agent 能用一个模块塞下所有内容**——拆是必要的；但自进化要求
  **模块间的数据必须流动**。

### 14.3 人怎么"了解一个人"——整体认知 vs 碎片仓库

- 人不会这样了解一个人："黑头发、高鼻梁、成绩好"（碎片拼接）；
- 人看到的是"这个人有风度"——**视觉、听觉、经验全部贯通成一个整体印象**；
- Agent 的对应物 = **用户模型（user model）**——不是特征碎片仓库，而是对用户的
  **可操作的整体理解**；
- bobo 现状：素材有（用户资料/记忆/Request/Obsidian/会话），**但没有汇聚点**
  形成整体理解 → agent 陷入被动，只能在"匹配到某条记忆"时才调用，无法主动
  贴合用户、无法和用户达成契约感。

### 14.4 自进化的落地 = 造"汇聚点"（evolved 用户模型）

```
记忆/会话/Obsidian/Request/反馈
        ↓ 提炼（各模块加工自己的素材）
    evolved（用户模型——单一汇聚点）
        ↓ 注入 + 驱动行为
    Agent 主动贴合用户（不靠被动匹配）
```

- **evolved 层 = 用户模型**：所有模块的产物（显式偏好 / 行为推断意图 / 纠正记录）
  汇入，形成整体理解；
- Agent 行动基于**整体模型持续主动贴合**（像秘书知道习惯，不用每次说），而非
  "命中记忆才响应"；
- 模块照样拆（可维护性），但**数据流汇入一个点**——"拆模块但打通"的架构答案。

### 14.5 对落地路径的影响

- 自进化 = **跨模块改造**（记忆沉淀通道 / 信号提取 / evolved 用户模型 / 注入 /
  可见层），不是单票能完成；
- 与既有规划衔接：P0 信号日志化 → P1 半自动建议流水线 → P2 evolved 自动固化，
  每一步都在"打通"这条数据流；第十三节 Messages 收件箱 = 流水线的用户可查环节；
- **待讨论**：哪些模块先打通（记忆→evolved？Request→evolved 升格？知识库参与
  意图学习？）。

## 十五、记忆模块设计：两大核心板块之一（2026-08-18 owner 阐述）

> owner：self-evolving 系统两个最大的核心板块 = **system prompts 部分** + **记忆部分**。
> 本节聚焦记忆部分的设计约束与多渠道打通。

### 15.1 现状问题（终审取证确认）

- **信息来源极窄**：记忆全部来自**对话**（save_memory 手动 + 压缩沉淀 +
  draft 条目）——"自己看用户在做什么，然后纳入一些记忆"；
- **与 Obsidian / library / docs 完全脱节**：knowledge_base.json 独立，injector
  只读 library（笔记指针）但不提炼进记忆；
- **无总量上限**：knowledge_base 已 656 条持续增长（只有注入预算，无库总量约束）。

### 15.2 约束一：限制总 token 数量

- 记忆系统**不能无限扩张**（否则一开始就消耗大量 token）；
- 现状：注入有预算（prompt_pool memory ceiling/floor），但**记忆库总量无约束**；
- 设计：记忆库总量上限（条数 / 总 chars）+ **淘汰机制**（低 signal 淘汰 /
  合并同主题 / 压缩旧条目）——与 token 预算呼应（库总量 × 注入比例 = 可控）。

### 15.3 约束二：多渠道提取记忆（微妙——不能乱提取）

- 目标：记忆来源从"单一对话"扩到 Obsidian / library / docs——"让记忆变得
  variety、diversify"，但不能乱提取；
- **"不乱提取"的机制（owner 指出的微妙处）**：
  1. **提取原则**：只提炼**关于用户的持久事实/偏好/模式**（用户模型导向），
     **不是**把知识库内容灌进记忆（知识库内容归知识库，记忆记"用户与知识的
     关系"）；
  2. **信号闸门**：提取候选 → 评估（LLM 判断 + 第 8.5 节 guidance）→ 高置信
     才入记忆（复用既有 signal_score 体系）；
  3. **来源标注**：每条记忆带来源（对话 / Obsidian / library / docs），可追溯；
  4. **频率/重要性**：用户反复查看某类笔记 → 兴趣信号（可提取）；单次查看 →
     不提取（防噪声）。

### 15.4 模块拆分但互通（owner 原则）

- "拆分模块永远不是我担心的事情，我担心的是模块之间互相隔离、不互通"；
- 记忆模块内部可拆：对话记忆 / 用户画像记忆 / 行为偏好记忆 / 知识关联记忆——
  但**共用一套 signal + 注入机制**，且**汇入 evolved 用户模型**（第十四节）；
- 设计原则：**拆（解耦可维护）+ 通（数据流汇入汇聚点）**。

### 15.5 与自进化系统的关系

- 记忆 = 自进化流水线的**输入源**（见第十四节数据流）——多渠道后，用户画像
  从"对话碎片"变成"多维度认知"（Obsidian 里的兴趣、library 里的工作模式、
  docs 里的纪律——全部汇入）；
- **待讨论**：多渠道提取的具体机制（提取触发时机 / 评估标准 / 与既有
  signal/decay 体系的融合）；记忆库总量上限的具体值（条数 vs chars）。

## 十六、Hermes 第三轮评估（2026-08-18，对 12-15 节的评审）

> 署名：Hermes（Nous Research）。对本设计最新五节（RL 机制/信任模型/Messages/
> 系统打通/记忆模块）的评审。**最重要的产出：evolved 应"投影而非存储"。**

### 16.1 认可的实质进步

- ✅ 12.2 渐进授权（低风险自动 + 高风险确认）——裁决了"人审 vs 无审批"矛盾；
- ✅ 13 节 Messages 收件箱——正确吸收"toast 骚扰"批判；
- ✅ 14 节"自进化=整个 agent 的逻辑"——定性正确；
- ✅ 15 节"记忆记关系不灌知识"——原则正确。

### 16.2 三处未闭合

1. **缓存红线零进展**（12-15 节无人碰）：尾部动态块改动是否破坏前缀缓存——**必须
   实测**，决定"高频微调"动作空间是否成立（money 问题）；
2. **淘汰判据盲区**：signal_score 是**内部一致性**指标（被引用+分），**不是准确性**
   ——错误记忆被系统自己引用 → signal_score 反而上升 → 更不被淘汰（**自举新通道**）；
   需补"负面淘汰"（用户纠正/回滚/删除 → 直接降权 + 降权其信号源）；
3. **EVAL 盲区**（体验退化测不出）仍挂在所有安全论证上，未回应。

### 16.3 记忆多渠道提取：一个根本坑

- **知识接触 ≠ 用户意图**：用户反复写 AI 主题笔记可能是工作职责，不是"希望 Bobo
  更懂 AI"——行为推断有语义 gap，且是 LLM 推断 + 无锚点信号（与 9.2 偏好自举
  同构）；错误提取入 evolved → 注入层 → 行为改变 → 自举；
- 缓解：来源类型权重（成文笔记 > 草稿）、内容成熟度判断（frontmatter 完整）、
  时间窗口（近 N 天反复才算，配合 decay）、增量扫描 + 后台异步（不进回合关键路径）。

### 16.4 记忆库总量约束：补"负面淘汰"

- 合理设计：总量按 token 预算反推（注入 ceiling × 注入比例的倒数 ≈ 库总量，
  用总 chars/tokens 而非条数）；
- 与 signal_score/decay 融合：淘汰主判据 signal_score（已有），**必须补负面淘汰**
  （纠正/回滚 → 降权 + 信号源降权，与 11.3-c 同机制贯穿到记忆层）；
- **注意**：总量约束只解决"存不下"，不解决"存了错的"——后者靠负面淘汰 + 准确性
  采样复核。

### 16.5 evolved 汇聚点：最大架构修正——投影而非存储（Hermes 核心产出）

- **风险**：14.4"所有模块产物汇入 evolved 单一汇聚点" = 从"模块间封闭"变成
  "**模块-汇聚点星型耦合**"——evolved 成新耦合中心，挂了全挂；
- **修正**：evolved 是**投影**，不是存储——各模块自有数据不动，evolved 只是
  "行为注入视图"，每次组装时从各模块**实时投影 ≤800 tokens 的用户模型片段**；
- 好处：不持有数据 → 不可能膨胀成大杂烩（knowledge_base 656 条失控 = 存储式
  汇聚教训）；模块仍解耦；回滚 = 改投影规则不碰源数据；
- **判断标准**：如果 evolved 需要自己的存储/淘汰/版本管理 = 第四个知识库 =
  架构失败；如果只是投影规则，才符合"拆但通"。

### 16.6 边界划分（什么进 evolved）

- **进**：显式偏好（用户说的）、行为推断（高频模式）、纠正记录（回滚/负面反馈）
  ——只收影响行为决策的用户属性；
- **不进**：知识内容（归知识库）、任务状态（归会话）、技能流程（归 skill-standards）；
- 8.3 的 ≤800 tokens 预算本身就是硬边界（放不下大杂烩）——保留。

### 16.7 P0 调整（Hermes 建议的第一步，有变化）

1. **信号日志化 ×2 通道**同时跑（两周）：对话信号（8.5 四条）+ 知识接触信号
   （反复查看/写入 Obsidian 的主题，只记录不提取）——一次实验验证两条通道；
2. **元学习授权边界列为最早验证项**：系统能否从"用户确认/忽略"行为中收敛出正确
   授权边界（信任模型地基，比信号质量更根本）；
3. **缓存实测排进 P0**：尾部动态块改动是否破坏前缀缓存（一行测试，决定 P2 经济
   模型）；
4. 简化：四级文档 → 先只做 evolved 投影层；多渠道先只做 Obsidian 一个源。

### 16.8 总结论（Hermes）

设计从"站不住"进化到"大部分站得住，但三处未闭合"：缓存红线零进展、淘汰判据
依赖 signal_score 却无视"内部一致性≠准确性"（自举通道）、evolved 汇聚点有演变
成第四个知识库的架构风险（**解决：投影而非存储**）。

## 十七、记忆分类设计：记忆不能一个池子装所有（2026-08-18 owner 阐述）

> owner：知识接触≠用户意图（同意 Hermes 16.3）。举例：重复做票子/代码任务时，
> 记忆不该记"每次票子的内容"（无价值），该记**用户每次做事的要求、偏好、不让做的
> 东西、做了什么**。记忆不只一种，必须**分类/拆模块**，混在一起结果不好。

### 17.1 现状（终审取证）

- v5_memory 有 entry_type 参数（压缩沉淀用 KEY_DECISION/USER_PREF/FACT），
  **但实际 656 条全部是空分类（'?'）**——全堆在 general 池，分类形同虚设；
- 印证 owner"把任何记忆都放到一个池子中 → 后面变得很混杂"。

### 17.2 五类记忆（功能导向分类）

| 类 | 记什么 | 例子 | 权重/注入 |
|---|---|---|---|
| ① 用户画像 USER_PREF | 偏好/习惯/沟通方式 | 中文回复、简洁、工作时段 | 高权重、高频注入（evolved 投影主源） |
| ② 行为约束 RULES | 要求 + 不让做 | 先跑测试、五查汇报、不要 emoji | **最高权重**、直接进规则层（不轻易淘汰） |
| ③ 事实/决策 FACT/KEY_DECISION | 用户教的知识、关键决策 | 项目事实、架构决策 | 中权重、按需提取（search） |
| ④ 成果 ACHIEVEMENT | 做过什么：完成的事、产出 | 完成的项目、交付的票 | 低权重、低注入（可追溯） |
| ⑤ 经验/教训 LESSON | 学会什么：成败模式 | 教训册 L1-L15 同型 | 中权重、场景触发 |

### 17.3 关键区分（防混杂）

- **任务状态**（进行中的票/会话）→ 归会话，**不进长期记忆**（Hermes 16.6）；
- **技能流程** → 归 skill-standards（已有）；
- 长期记忆只留：画像 + 约束 + 事实 + 成果 + 经验；
- **"做了什么"的定位**：成果类（完成的、可追溯的）进长期记忆；进行中的归会话。

### 17.4 分类的价值

1. **信号权重不同**：行为约束 > 画像 > 事实 > 成果（错误记忆在不同类危害不同）；
2. **注入策略不同**：画像/约束高频注入（evolved 投影主源），事实按需查，成果低注入；
3. **淘汰策略不同**：约束不轻易淘汰（尤其负面约束）、画像可更新、事实可过期
   （decay 速率按类调）；
4. **与 Hermes 衔接**：负面淘汰（纠正/回滚 → 降权）按类落实；evolved 投影按类取片段。

### 17.5 落地

- 不新建体系：扩展 v5_memory 既有 entry_type（KEY_DECISION/USER_PREF/FACT +
  新增 RULES / ACHIEVEMENT / LESSON）；
- 修历史数据：656 条空分类迁移归类（按内容启发式 + 人工抽查）；
- 与信号体系融合：signal_score / decay 按类调参（约束慢衰减、事实正常衰减）；
- 与 evolved 投影（16.5）衔接：投影时按类取片段（画像+约束为主源）。

## 十八、记忆与 library 的串通：数据流设计（2026-08-18 owner 阐述）

> owner：记忆和 library 是"串通"的（不是捆绑）——数据流互通。会话内容已经有
> library 这个存储地了，**没必要重复进入记忆空间**；但记忆和 library 不能完全
> 隔离，**记忆得有办法和 library 互通**。自进化系统所有东西必须通，不能独立。

### 18.1 取证确认（library 自动记录机制）

- `tools/living_notes.py`：**收工时（RESPONDING，takeaways 非空）自动把本轮要点
  写进 `library/<领域>/<主题>.md`** + 维护 index.md（engine.py:1322-1341 触发）；
- library 现状：9 个领域目录 + index.md + MEMORY.md，259 个 md 文件；
- **确认 owner 判断**：会话内容的长期沉淀地 = library（自动，无需人工）。

### 18.2 数据流（"串通"的精确定义）

```
会话内容 ──自动──▶ library（living_notes，已实现）
                      │ 内容存这里（记忆不重复存）
                      ▼ 提炼"用户模型信号"（17 节五类，画像/约束为主）
记忆（knowledge_base）──存画像/约束（不存会话内容副本）
                      │ 引用/索引互通（记忆条目 → library 笔记链接；
                      │  library frontmatter source_sessions 反查会话）
                      ▼ 投影
evolved 用户模型 ──注入──▶ 行为
```

### 18.3 核心原则

1. **会话内容有 library 存了 → 记忆不重复存**（避免重复存储/膨胀）；
2. **记忆 ↔ library 串通**：记忆存"用户模型"（画像/约束），library 存"内容"，
   两者通过**引用/索引**互通（记忆条目带 library 链接；library 笔记
   source_sessions 可反查来源会话）；
3. **自进化 = 全通**：会话 → library → 记忆 → evolved → 注入 → 行为，一条数据流，
   无孤立模块（14.2 原则的落地）。

### 18.4 对 17 节五类记忆的修正

- **事实/成果类应存"指向 library 的指针"而非内容副本**（如"你做过 X 项目" →
  指向 library 项目笔记，不复制项目内容进记忆）——记忆天然变薄，只留画像/约束
  这类"用户模型"核心；
- 656 条空分类历史数据中，疑似有"重复存的会话内容"——迁移归类时按此原则清理
  （能指向 library 的改指针，纯内容副本可归档/降权）。

## 十九、记忆 = 信号抓取中枢（2026-08-18 owner 阐述，方向澄清）

> owner：记忆不能硬编码、不能固定，来源必须广泛——甚至用户操作桌面的行为都可
> 以进记忆。记忆不是所有东西都进，而是**拉着其他区块浓缩后给用户反馈**——
> 记忆是一个"抓取/提炼中枢"，不是存储库。

### 19.1 记忆的定位升级

- **记忆 = 信号抓取/提炼中枢**（不是一个大 JSON 存储）：
  ```
  来源（广泛、非硬编码、非固定）：
    对话（8.5 信号）│ library（bobo 工作记录）│ Obsidian（用户个人知识）
    docs（纪律）│ 桌面操作（UI 行为）│ Request（显式设定）
          ↓ 抓取信号（不是搬内容！）
  记忆中枢：提炼 → 用户模型（画像/约束）→ 反馈（Messages 收件箱）
  ```
- **抓取的是"用户与内容的关系"信号**（反复写某主题 / 用某功能频率 / 不让做的），
  不是内容本身（内容留在 library / Obsidian）。

### 19.2 Obsidian 加入记忆

- 定位：Obsidian = **用户主动写的个人知识**（vs library = bobo 自己写的工作记录）
  ——都是"用户与知识的关系"信号源；
- 信号提炼（不搬内容）：反复写某主题 → 兴趣/工作模式信号；frontmatter/标签 →
  结构化信号；**防 Hermes 16.3"知识接触≠意图"**（反复写可能是职责）；
- 互通：记忆条目可指向 Obsidian 笔记（引用）。

### 19.3 桌面操作进记忆（非语言交互）

- 用户操作桌面（点开什么 / 功能使用频率 / 从不做什么）→ UI 行为信号；
- 实现：前端轻量行为埋点 → 信号采集（**隐私边界：只采行为模式，不采内容**）；
- 例：频繁用"代码审查"功能 → 工作模式信号；从不点某功能 → 负信号。

### 19.4 信号分级 + 来源可信度（DeepSeek 补充，加固 Hermes 16.3）

| 来源 | 可信度 | 例子 |
|---|---|---|
| 用户明说（Request / 对话） | 🔴 最高 | "以后都用中文" |
| 行为推断（桌面操作 / 频率） | 🟡 中 | 频繁用某功能 |
| 知识接触（Obsidian / library） | 🟢 最低 | 反复写某主题（可能是职责） |

- 提炼按**可信度加权**：不是不采知识信号，而是它权重低、需更多佐证才升格；
- 回应 Hermes 16.3：知识接触信号只作"弱候选"，需与明说/行为信号共振才入用户模型。

### 19.5 架构含义

- 记忆不再是一个 JSON 库，而是**多来源信号 → 提炼 → 用户模型**的管道；
- 与 18 节呼应：内容归内容库（library/Obsidian），记忆记"用户与内容的关系"；
- 与 16.5 呼应：evolved 是投影（从用户模型投影行为片段）；记忆中枢是提炼层
  （从各来源提炼用户模型）——**全系统"内容/提炼/投影"三层分工**。

  机制（16.3 提取成本）。

## 二十一、Hermes 第四轮终评（2026-08-18，对 15-20 节记忆设计）

> 署名：Hermes。结论修正：**"缩小做"→"分块做"**——记忆重构可独立先行
> （有独立价值），自进化核心（evolved 自动固化）仍不该开。

### 21.1 前三轮坑的验收

| 坑 | 状态 |
|---|---|
| 大杂烩 / evolved 第四个知识库 | ✅ 闭合最好（17/18/20 节转向正确） |
| 知识接触≠意图（9.2/16.3） | ✅ 实质回应（19.4 可信度分级） |

| 内部一致性≠准确性（signal_score 自举通道） | ❌ 零回应 |
| 缓存红线 | ❌ 零进展 |
| EVAL 盲区（体验退化测不出） | ❌ 零进展 |

### 21.2 三个结构性新增

1. **漏类：用户目标/优先级**——用户当前在追求什么（目标≠画像（时变 vs 恒定）、

   用户喜欢什么，不知道用户要去哪）；

   - 画像 vs 约束：**违反它用户会不会纠正/不满？会→约束；只是不贴合→画像**；

## 二十三、记忆系统终稿骨架：分层存储 + 主动触发 + 修正模型（2026-08-20 Hermes 整理）

> 署名：Hermes。本节是 8-20 与 owner 连续讨论的整理——从"记忆要主动"出发，
> 推演到"prompt 也应自进化"，最终收敛为记忆系统完整骨架（存储/触发/修正/反馈
> 四层）。owner 拍板：**先工程兜底（GUI-T1/T2/T3 已落地），再讨论实现本骨架**。

### 23.1 存储层：身份层进 prompt，任务层进记忆库（owner 决策）

**五类记忆拆成两层，存储位置按"使用频率"决定（注入式 vs 检索式）：**

| 层 | 类别 | 存储 | 使用方式 |
|---|---|---|---|
| 身份层 | 用户画像 / 行为约束 | **prompt 文件**（常驻） | 注入式（每轮在） |
| 任务层 | 事实决策 / 成果 / 经验教训 | **记忆库**（检索） | 检索式（按需触发） |

**这一分层同时解决三个此前无解的问题：**
1. **误触发根治**：画像/约束不在记忆库 → 技术讨论时根本不可能误触发（存储层
   杜绝，不需要触发阈值去拦）；
2. **缓存红线化解**：身份层低频稳定更新（画像不会天天变）→ 前缀缓存友好；
   任务层检索式（查询不进 messages）→ 不破坏缓存——两个都不碰缓存红线；
3. **主动形态**：身份层常驻 = 天然主动；任务层自动触发 = 主动检索。

> owner 补充：prompt 也应是自进化的——prompt 随用户使用自动更新，才能持续
> 贴近用户。Hermes 确认：这正是 Claude Code CLAUDE.md / Cursor rules 的主流
> 实践，但 Bobo 更进一步（prompt 本身自进化）。

### 23.2 触发层：目录常驻 + 确定性匹配 + LLM 从候选选

**"主动"的正确形态是三层混合（不是全量注入——token 预算/缓存会爆炸）：**

```
L0 被动（现状）：用户问"你记得吗" → bobo 才查（"不调用就不了解用户"）❌
L1 自动触发：bobo 看到任务 → 自动判断该用哪类记忆 → 主动检索注入 ✅
L2 画像常驻：身份层每轮在上下文中（prompt 常驻，不占注入预算）✅
```

**触发判断分层（堵 9.2 自举通道）：**
- 第一层**确定性信号**（代码算）：主题词/实体/工具名/任务类型 → 与记忆的
  场景标签匹配 → 出候选；
- 第二层 **LLM 语义**：只对候选列表排序/精修——**LLM 永远不面对空白**，
  不能凭空发明"该用记忆 X"。

**渐进式触发（学 Hermes skill 机制，解决主动 + 缓存 + 成本）：**
```
记忆目录（信号标签+一句话摘要）常驻 prompt —— 低 token、稳定、不破坏缓存
→ bobo 每轮"看得到"有哪些记忆可用（满足"主动"）
→ 需要时展开某条完整内容（按需查询，不进 messages，不破坏缓存）
```

**误触发 vs 不触发（owner 担忧：技术讨论时调出画像类记忆）：**
- 误触发危害 >> 不触发（不触发=中性；误触发=用户觉得 bobo 没听懂）→ 阈值偏高
- 技术任务里确定性信号（工具名/文件路径/报错）比语义匹配可靠
- 误触发最后防线 = 可见性（用户看到"📎 用了记忆"立刻可纠）

### 23.3 修正层：置信度加权 + 证据链 + 惯性死区（owner 核心思想）

**"prompt 和记忆都应是修正的过程——不只增不减，而是不断修正使其更符合
用户习惯"（owner 原话）。**

**修正 ≠ 增删，修正 = 持续逼近（approximation）：**

```
每条（prompt 规则/记忆）携带 { 内容, 置信度, 证据链 }
新证据 → 按证据强度调整置信度（不是重写内容）
单次反馈 → 只动摇置信度（用户一次"可以再详细点" → 0.8→0.6，不改内容）
多次一致反馈 → 置信度跌破阈值 → 内容翻转/降级
置信度升过上限 → 规则固化（进 prompt 常驻）
```

**三个机制问题（修正最难的部分）：**
1. **方向**：修正方向必须来自用户证据（显式反馈+行为证据），不能来自系统
   自我感觉（LLM 发明方向 = 自举）；
2. **幅度**：置信度加权而非替换（单次反馈不重写内容）；
3. **振荡**：惯性（阻尼）+ 死区（置信度 0.4-0.6 中间地带不触发翻转）。

**证据链是信任基础**：每次修正记录"因为什么改的"（用户某天某话）→ 回滚
有据可查、审计可追——与审计日志（护城河）自然延伸。

### 23.4 反馈层：用户显式反馈驱动（RL 结构 + 三坑）

**记忆系统 = RL 结构（owner 类比）：action=触发记忆，reward=用户反馈，
信号分=权重更新。**

| RL 概念 | Bobo 记忆系统 |
|---|---|
| action | 触发/调用某条记忆 |
| reward | 用户显式反馈（认可/反对） |
| 稀疏奖励 | **沉默 = 无更新（不是正奖励！）——钉死，堵自举** |
| 信用分配 | 反馈归因：记忆内容错 / 触发时机错 / LLM 表达错 |
| 梯度更新 | 信号 ±Δ（反对大幅、认可小幅、上限防爆炸） |
| 灾难性遗忘 | 负面淘汰（多次强烈反对才删除） |

**用户反馈的幅度设计：**
```
明确认可   → +Δ（有上限，防自举放大）
沉默       → 不更新（关键！沉默≠认可，否则回到 9.2 自举）
轻微不满   → -Δ（小幅）
强烈反对   → -大Δ + 标记负面（触发层降权）
多次强烈反对 → 删除候选（负面淘汰落地）
```

### 23.5 与既有设计的关系（统一模型）

本节把此前碎片统一成一个模型：**每一条知识都是带置信度的假设，用户交互是
检验，反馈是更新，收敛是目标。**

| 既有设计 | 在本模型中的角色 |
|---|---|
| 19 节来源可信度分级（明说>行为>知识接触） | 初始置信度的来源 |
| 16 节负面淘汰 | 置信度跌破下限的处置 |
| 12 节渐进授权 | 置信度高的规则自动固化进 prompt |
| 11 节回滚振荡 | 惯性 + 死区机制 |
| 22 节 Memory 模块（可见层） | 修正的可视化通道（diff 显示） |
