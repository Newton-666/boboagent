## 一、病灶（已定位，直接引代码）

`core/engine.py` RESPONDING 状态（~938 行）：**每个回合收尾都无条件调 `_extract_takeaways()`**，而它内部（~459 行）是一次完整的 `self.llm_caller(prompt, use_tools=False)` API 调用。

后果：
- 用户说"谢谢""好的""继续"这种闲聊回合，也烧一次 API
- 每次调用都带 system prompt + 上下文，几百到上千 token/回合
- 回合收尾延迟 +2~5 秒（等这次调用返回），是"收工慢"的隐性来源之一
- 绝大多数返回"无"——白烧

## 二、处方：本地启发式闸门（零 LLM 成本预筛）

在 `_extract_takeaways()` 入口加一个 **纯本地、无 API 调用** 的预筛函数 `_takeaway_worthy(user_msg, asst_msg) -> bool`。不值得的回合直接 return []，根本不打 API。

### 预筛规则（跳过方向，命中任一即跳过）

1. **短闲聊**：user 和 asst 的内容均 < 40 字，且不命中任何价值关键词
2. **纯确认/过渡**：user 内容匹配 `^(好的|好|嗯|行|ok|OK|谢谢|继续|收到|对|是的?|可以的?)[。！!~\s]*$` 类模式
3. **纯问答无沉淀**：asst 内容 < 60 字且无价值关键词

### 放行信号（命中任一即放行，宁可多打不可漏记）

- 价值关键词：`决定|以后|记住|偏好|喜欢|习惯|以后都|改成|不要再用|规则|流程|选型|方案定|上线|部署|密码|密钥|配置`
- 内容足够长（user > 100 字 或 asst > 200 字）——长内容默认有沉淀价值
- 工具执行回合（本轮有 tool.exec 事件）——工作回合默认值得筛

**原则：预筛宁可保守放行（多打一次 API），不可误杀（漏记用户偏好）。漏记的代价比多打一次 API 大。**

## 三、配套要求

1. **可观测**：跳过时写事件总线 `takeaway.skipped`（含触发规则名）；提取时写 `takeaway.extracted`（含条数）。以后能用 events.jsonl 算出跳过率，验证省了多少。
2. **总开关**：环境变量 `BOBO_TAKEAWAYS=off` 时整个功能关闭（连闸门都不进）。
3. **不动提取本身**：prompt、解析、写 v5_memory 的逻辑一行不动。
