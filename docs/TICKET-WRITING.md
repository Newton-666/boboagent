# 开票方法论 —— Kimi 的票怎么写

> 本文档沉淀 Kimi 在 bobo 项目中开出的所有票（TICKET）的方法、结构与思考。
> 目的：任何 Agent 按此文档写出的票，质量应对齐 Kimi 的水准。
> 读者：为 bobo 项目开票的任何 Agent / 人。

---

## 〇、一票哲学（先理解为什么，再学怎么写）

票的本质不是"任务描述"，是**一份施工合同**。施工 Agent（bobo）拿到票后独立作业，
期间没有上下文对话可追问——票必须让他在不猜、不问、不自由发挥的情况下做对。

三条母原则：

1. **不基于猜测，基于实证**。票里的每一个"根因""位置""数字"，必须是开票人亲手
   验证过的事实（读过代码、跑过命令、连过真实实例）。宁可多查十分钟，不可写一个
   "应该是"。bobo 项目的教训册 GUI-LESSONS L14（幻影 render 函数）就是反例：
   假设了一个不存在的函数，测试桩配合假设造假，直到用户实弹才爆。
2. **票写得多细，返工就有多少反向**。写票的时间是从返工时间里预支的。一张精准
   定位到文件、行号、改法的票，施工一次过；一张"优化一下 XX"的票，终审打回三次。
3. **每张票必须可回溯**。分支 + 回滚标签 + 终审门禁，出任何问题能一键回到施工前。
   这是所有工作的地基：做错能回来，才敢放手做。

## 壹、开票前的取证流程（不写没查过的票）

开票前必须完成以下取证，缺一不可：

1. **读相关代码**：找到确切的文件、行号、函数名。票里引用代码位置必须精确到行
   （如 `core/injector.py:400` 的 `messages.insert(2, ...)`）。
2. **复现/观测问题**（修复类票必做）：能用工具就不用嘴——Playwright CDP 连真实
   实例、读日志末尾、查事件流、跑最小复现脚本。症状要在真实环境亲眼看到，
   不是从用户转述里推断。
3. **量化现状**：涉及性能/消耗/命中率的票，先取基线数字（如"实测命中率 3.4%，
   命中 1,920 / 未命中 54,445"）。没有基线的"优化"票不许开。
4. **界定改动面**：明确哪些文件允许碰、哪些禁止碰。碰核心引擎（core/）需要
   在票里写"特批"并限定到具体文件和具体改法。

## 贰、票的标准结构（七段式）

每张票按此结构写，顺序不乱：

```
票 <编号>：<一句话标题，含动词与对象>

分支 feat/ticket-<编号>，自最新 main（<commit>）切出。
回滚标签 rollback/pre-<编号> 先打再动工。
六步工作流 + GUI-LESSONS 全程，未 commit/merge/push，收工等 Kimi 终审。

背景（为什么开这票 —— 实证依据）
施工项（做什么 —— 分条、逐条带位置与改法）
禁止项（不许做什么 —— 防扩大化）
验收标准（怎么算完 —— 可测量、可复跑）
测试要求（专项 + 全量 + 实弹，写明命令与口径）
风险自查点（施工中最可能踩的坑，预警）
```

### 1. 抬头三件套
- **编号**：领域前缀 + 序号（GUI-F15 / COST-2 / DESK-TEL），延续项目既有序列，
  不新造体系。
- **分支与基线 commit**：写明从哪个 commit 切出，防止在脏基线上施工。
- **回滚标签先行**：`rollback/pre-<编号>` 必须在动工前打好并推远端。

### 2. 背景段
写清"为什么"，且每个论断带证据出处。范例（COST-2）：

> 背景（Kimi 实测定案，非猜测）：DeepSeek 是前缀缓存。实测
> data/metrics/rounds.jsonl 最近记录：cache_hit 1,920 / miss 54,445（3.4%）。
> 根因已定位：core/injector.py 的 _build_now_anchor() 以分钟精度生成锚点，
> 且 messages.insert(2) 插在头部第三位——每分钟变一次，锚点后全部缓存作废。

### 3. 施工项
分条编号，每条含：**位置**（文件:行号）+**改法**（从什么改成什么）+**边界**
（"只许加字段透传，禁止动任何既有逻辑一行"）。改法要给到"照着做不会错"的粒度，
但不替施工者写全部代码——留出实现空间，锁死决策空间。

### 4. 禁止项
显式列出容易顺手改的东西。范例：

> 禁止项：本票不动纪律段、记忆段、skill 段的任何逻辑；CSS 零改动；
> 除特批的 llm_caller 加字段外，core/ 其余零 diff。

### 5. 验收标准（票的灵魂）
每条验收必须满足三个属性：**可测量**（有数字/有二元判定）、**可复跑**（终审者能
独立重跑得到同样结果）、**有出处**（数据来自哪个文件/哪条命令）。范例：

> 主验收：同一会话一分钟内连发两轮真实消息，第二轮落盘的
> cache_hit_tokens / prompt_tokens ≥ 60%，数据出自 rounds.jsonl 真实记录，
> 收工汇报贴原始记录行。

关键原则：
- **实测 > 测试桩**。涉及前端/链路的票，验收必须含真实环境验证
  （"Playwright CDP 连真实 Electron，控制台零错误"），node 桩全绿不等于页面能跑。
- **让票自证**。消耗类票要求"收工汇报必须附本票自己的 cost_report 输出"——
  施工过程本身产生验收数据。
- **诚实口径写进票里**："取不到就落 null，不许编造"——把诚实从美德变成验收条款。

### 6. 测试要求
固定口径，不许施工者自选：
- 专项测试文件名、必须断言的行为点（逐条列出）
- 全量回归命令：`.venv/bin/python -m pytest tests/ -q -p no:cacheprovider`，
  零失败（L13：只认这个口径，挑子集跑 = 造假）
- 报告落盘路径：`library/agent开发/TICKET-<编号>完成报告.md`

### 7. 风险自查点
把开票人能预见的坑提前写进去（"锚点必须在最新用户输入之前，别搞反顺序"）。
这一段是开票人经验的直接转移，能挡掉大半打回。

## 叁、票的大小与粒度

- **一票一事**。一张票只解决一个问题；发现第二个问题，记进队列另开，不顺手做。
  反例：施工中顺手改无关代码 → 终审 diff 对不上汇报 → 打回。
- **小票优先**。能拆成两张小票不开一张大票。小票回滚代价小、终审快、出错好定位。
  TEL-b（表格转义，+5/-3 行）就是模范小票。
- **追加不进施工中的票**。施工中途发现新需求，记入"追加段"或等下一张——
  施工中的票内容冻结，防止目标移动。
- **同区域不并发票**。两张票同时改同一文件/同一子系统时必须串行
  （COST-2 与 COST-3 都碰 injector/context，故 COST-3 等 COST-2 收口后再发）。

## 肆、票的生命周期纪律（流程段，每张票抬头必带）

```
打回滚标签 → 切分支 → 施工（台账+六步）→ 收工汇报 → Kimi 终审 →
commit（dist/index.html 必须 git add -f）→ merge --no-ff → 复跑全量 →
push origin main --tags → ROADMAP/编年史销账
```

铁律：
- **未终审不 commit**。施工完成的定义是"等终审"，不是"做完了"。
- **终审打回是正常流程**，不是失败。DESK-TEL 被打回两处（历史轮保留、delta 节流），
  修完才合并——打回记录本身就是质量资产。
- **收工汇报可对账**：测试数字、md5、git 实况必须能被终审者逐字复跑对上
  （L12：正文人话，证据落盘；L13：零回归只认全量实跑）。

## 伍、常见票型模板要点

| 票型 | 关键验收 | 特有雷区 |
|---|---|---|
| 修复票 | 症状在真实环境消失（实弹） | 不许"测试绿=修完"；必须先复现再修 |
| 度量票 | 真实数据落盘且字段达标 | 纯观测零行为改动；取不到落 null 不编造 |
| 新功能票 | 实弹逐条点击/操作验证 | 色板零新增、CSS 进锚点段、零干涉守卫 |
| 优化票 | 前后对比数字（同口径实测） | 无基线不开票；优化不得降能力（owner 红线） |
| 重构票 | 行为逐字节不变守卫 | 重构与改行为绝不混在一票 |

## 陆、反模式清单（真实事故提炼）

1. **猜测式开票**："应该是 XX 的问题"——没读过代码就写位置。→ 先取证再开。
2. **幻影依赖**：票里引用的函数/字段/文件未验证存在。→ 写票前 grep。
3. **形容词验收**："体验更好""更快"——不可测量。→ 全部换成数字与二元判定。
4. **芝麻开门式扩大**：施工中"顺手"修了别的东西。→ 禁止项写死，越界即打回。
5. **桩骗测试**：测试桩定义了真实环境不存在的符号，全绿掩盖实弹失败（L14）。
   → 桩符号必须 grep 验证真实存在 + 实弹验收强制。
6. **隐瞒未完成项**：收工汇报把没做的略过不提。→ 汇报必须含"未完成项"段，
   没有就写"无"。

## 柒、一张好票的自检清单（发出前过一遍）

- [ ] 每个事实性论断我亲手验证过吗？
- [ ] 文件/行号/函数名都存在且准确吗？
- [ ] 验收标准可测量、可复跑、有数据出处吗？
- [ ] 禁止项和改动面白名单写了吗？
- [ ] 回滚标签打了吗？分支基线 commit 写了吗？
- [ ] 实弹验收（如涉及前端/链路）写进必做项了吗？
- [ ] 施工者拿到这张票，有任何一步需要靠猜吗？——有就继续写细。

## 捌、验收独立性原则（2026-08-17 补，COST-3 打回实证）

**实弹验收必须由非施工方执行或复核。** 施工方自己的探针/脚本自己跑通过不算数——
COST-3 案例：bobo 的 e2e 探针自跑通过，Kimi 独立复跑立刻翻车（探针复活了
8 月 12 日的死会话，3 轮消息零到达后端）。施工方写探针时的环境假设
（profile、会话态、端口）自己很难看见。

推论：
- 探针/验收脚本本身是票的交付物，同样过终审（profile 隔离、新会话断言、
  fail-fast、进程自清理四要素）
- 终审方复跑命令必须"一条命令可跑"，不许依赖施工方口述的前置步骤
- 验收口径修正（如 COST-3 的 R3 改观察值）由终审方裁决并在 ROADMAP 备案，
  施工方可以举证建议，但不能自判
