## 0. 一句话结论

微信/邮件这类东西**不是"额外工具"，是"通道"**——Agent 在微信里有一个自己的身份（微信号），用户可以在不同场所（微信/桌面端/邮件）跟同一个 Agent 对话。接入它们的目的不是"加一个会聊天的功能"，而是**让 loop 触达用户的真实生活**。

## 1. 核心认知转变（owner 对齐）

- ❌ 错误理解：微信是 Hermes 可以接入的一个额外 tool（桌面端输入 → 调用微信 → 结果回桌面端）。
- ✅ 正确理解：**Hermes 有自己的微信号**（扫码登录绑定 bot 号），用户加它为好友，在这个聊天里直接跟 Hermes 对话。**从哪个口进来，就从哪个口回应**——桌面端和微信是平行通道，同一个 agent、同一套记忆，只是对话发生在不同场所。
- Hermes **不碰用户的私人微信**：不读私人号聊天记录、不代替收发、不操控。Hermes 只在它自己的 bot 号上存在。

## 2. Hermes 微信接入逻辑（技术路线参考）

- 技术路线：腾讯 **iLink Bot API** 接微信个人号（`ilinkai.weixin.qq.com`），非企业微信（wecom 是另一套）。
- 入站：`getupdates` 35s 长轮询循环，增量游标落盘（断线续传），会话过期暂停、限频退避。
- 出站：`sendmessage` POST，每条回复必须回显该聊天的 `context_token`（过期自动降级重试）。
- 媒体：AES-128-ECB 加密腾讯 CDN 协议。
- 认证：QR 扫码登录拿 `bot_token` + `account_id`，凭证落盘。
- 传输级策略在适配器内：文本防抖批量、内容去重、私聊/群聊策略、限频熔断。
- 微信消息不可编辑 → 跳过流式，回复一次成型。

## 3. Hermes 通道架构模式（值得借鉴的"枝条形态"）

- `platform_registry.py`：`PlatformEntry` 元数据自注册（怎么建/要什么环境变量/怎么验证配置/LLM 提示/授权/消息上限），插件可覆盖内置，**加平台零核心改动**。
- `base.py` 平台契约**很薄**：抽象方法只有 `connect / disconnect / send / get_chat_info`；入站约定 = 归一化成 `MessageEvent`（带 `SessionSource`：platform/chat_id/chat_type/user_id/thread_id）→ `handle_message()` 上抛。
- **边界**：平台只做"收发 + 传输级策略"；鉴权、会话、agent 语义全在核心。
- **会话**：每个聊天一个会话（`build_session_key` → `get_or_create`）。
- **事件渲染**："agent 决定发生了什么、adapter 决定怎么渲染"——类型化事件，通道可"吃掉"不支持的事件。

## 4. 思路评估（对不对）

成立点：
- 契约薄、元数据厚——平台实现最小收发 + 上抛，其余统一在核心。枝条就是枝条。
- 事件渲染边界——通道决定渲染什么/吃掉什么，对应"节点必长叶但允许通道裁剪"。
- per-chat 会话隔离；传输级策略留在通道内（防抖/去重不污染走廊）；自注册零核心改动。

不能学的：
- 不拼代码（他们 asyncio + 自家事件词汇表 + 自家会话系统，和我们的走廊不匹配）。
- 不学规模（`run.py` 16000 行是历史堆积；我们只学"通道抽象"这一层）。
- 微信走 iLink 是第三方服务（个人微信无官方 API 的务实选择），第三方稳定性/合规性是接入前评估项，非架构问题。

## 5. 与我们的接口/loop 差异

| | Hermes | 我们 |
|---|---|---|
| 驱动模式 | 通道驱动（平台推消息进 loop，定向回复） | RPC 驱动（prompt.submit 请求 → 事件广播回） |
| 会话模型 | per-chat 会话（每个聊天一个 session） | 单会话引擎（一个 sid 一个引擎线程） |
| 输出模型 | 定向投递（send 到 chat_id + reply_to） | 事件广播（emit → 客户端按 session 过滤） |
| 并发模型 | asyncio 全链路 | 线程 + 事件总线 |
| 事件 | 类型化事件词汇表 + adapter 渲染 | emit 事件 + GUI 固定渲染 |

结论：学契约形状，接自己的走廊。

## 6. 宏观契合（磁场/收束框架，owner 定）

- **树是发散模型，Agent 是收束模型（磁场）**：功能的本质是往外发散，发散不收回来就是变乱的根源。Agent 架构必须向心——工具产出、通道信号、用户反馈，全部回流 loop 中心被消化（观察 → 学习 → 记忆 → 适应 → 沉淀），再释放。
- **"不违和"的判断标准**：一个新东西放进 harness，是**落到 loop 已有的环节上**（叠加），还是在旁边**另起炉灶**（发散）。
- **叠加 vs 变乱**：变乱 = 每加一个东西就多一套独立逻辑，零件堆砌互不沟通；叠加 = 只增加"输入来源/输出渠道"，核心环节一个没多一个没少，但每个环节更丰富。
- 微信的宏观意义：Agent 从"你在电脑前打开它才存在"变成"在你生活的地方持续存在"——loop 形状不变，但它开始跟着用户的生活转。

## 7. 价值判断（为什么"总结邮件"本身没有价值）

- 孤立功能（"帮我总结一下邮件"）是一次功能调用，没进 loop → 没价值，十几个小时不值。
- 有价值的是：通道持续进观察流，Agent 学习用户的工作节奏/习惯 → 在合适时机主动服务 → 用户反馈成为奖励信号 → Agent 成长。
- 这正是范式里已有的：**观察通道 vs 奖励通道**；RL = 观察 → 累积 → 落笔。通道给 RL 提供了真实世界的输入来源。

## 8. 参照系（Outlook / 邮件）

- Hermes `msgraph_webhook.py`（微软 Graph webhook）：Outlook/Exchange 变更通知入站。
- Hermes `email.py`（IMAP 收 + SMTP 发）：通用邮件，QQ 邮箱同款路线。
- 复杂度排序（对我们）：email 最简单 < Outlook（Graph）中等 < 微信（iLink）最复杂。

## 9. 待定决策（owner 再思考时过一遍）

1. 技术路线：iLink 个人号（Hermes 同款）vs 企业微信官方 API。
2. 接入形态：通道只做收发，还是按"loop 接入"（信号回流观察流 + 反馈进奖励通道 + 主动服务投递口）。
3. 时机：现在不加，等 harness 主干再稳一稳 / 或先做更简单的通道验证契约。
4. 会话映射：per-chat 稳定 sid（如 `wx-<chat_id>`），复用现有 session 持久化。

## 10. 若将来实施（方向，非细节）

- 挂在 `bobo_tui_gateway` 层，走廊一行不动（引擎、事件总线、压缩、工具面、现有 GUI/TUI 通道）。
- 输入口：微信消息 → 归一化 `{platform, chat_id, text, media}` → 稳定 sid → 走现有 `prompt.submit`/`run_engine` 进引擎。
- 输出口：引擎事件 → 通道渲染器（最终回复必发；工具卡/思考可摘要或吃掉）→ adapter.send()。
- 传输级策略（防抖/去重/context_token）全在适配器内部——枝条内部的事。
