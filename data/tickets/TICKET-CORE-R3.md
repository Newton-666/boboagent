# TICKET-CORE-R3 —— 答复压制源排查与拆除（P0）

> 施工前必读 docs/GUI-LESSONS.md。分支 feat/ticket-core-r3（自最新 main 切出）。未终审不 commit。

## owner 定调（2026-08-14，本票最高指导原则）

**"回复是自然反应，不需要额外机制。它一定是被哪个东西卡住了、限制住了，而不是不会。"**
本票以**找出并拆除压制源**为目标。禁止叠新机制、禁止加新闸，除非诊断证据确凿证明别无他法（且需 Kimi 特批）。

## 病症

思考过程分条列点质量很高，最终回复却缩水成"任务已全部完成"一两句；问答回合所答非所问（问"之前做了什么"答成台账交账）。

## 嫌疑清单（按嫌疑度排序，逐个取证排除或坐实）

1. **收工闸/字段闸打回重试**：打回后模型第二次生成的回复是否显著缩水（"少写少错"心态）？查打回前后的回复原文对比
2. **台账摘要/对账段注入**：LEDGER-1B 后对账段改内部注入——注入的指令是否诱导模型把"交账"当成交替答复？
3. **系统提示词纪律段过载**：纪律/闸门/拦截说明占了多少字？答复相关指令是否被淹到模型注意力的尾部？（injector 有 prompt.budget 事件，用现有埋点量）
4. **max_tokens / 流式截断**：答复是否被截断后兜底成短句？
5. **R2b 质量闸自身**：打回重答的引导语是否反而把回复压短了？

## 附录：外部取证报告（2026-08-14，另一 agent 对 events.jsonl 的解剖，已坐实根因链）

数据面（最活跃会话 20260812_231407）：最后 15 次收尾调用 10 次 completion_tokens=0；全库 goal_gate.deny 799 次 ledger_backfill + 106 次 ledger_field_missing。

典型死循环（08:06:17→08:06:40 实记）：R2b 打回 → 收工闸 deny → 空回复 ct=0 → 再打回 → 再空 → 熔断放行。用户拿到的回复=被闸门折腾后的残骸。

三闸叠加误伤（代码位置已定位）：
1. engine.py:659-671 `_detect_ledger_backfill`：做完活最后一次性登记台账全标 done = 正常收尾，被判"事后补账"→ deny（799 次/库，非偶发）
2. engine.py:1799-1812 R2b 质量闸：回复以 📋/台账/完成项 开头且 <120 字 → 打回；豁免仅限"本回合含写类工具"（:2084），读/查类正常收尾必被打回
3. verifier.py:14-17 完成词过宽："完成"/"阶段"两字词任何回复都有 → 注入"请提供具体证据"

次生：空回复进沉淀线程 → notes.error（空内容调 LLM 提取失败）。

## 施工方案（按外部报告修复方向落地，四刀全是收窄/拆除，符合"不加新机制"）

- [ ] R3-a `_detect_ledger_backfill` 加施工证据豁免：create 后存在任何非 ledger 工具轮（真实施工痕迹）→ 全 done 不算补账。补账的本质是"没干活直接标 done"，不是"干完活再登记"
- [ ] R3-b R2b 豁免面扩大：`_round_had_write_tool` 之外加"本轮 tool.exec ≥ N 次"施工证据豁免（有实际执行就不算空口台账腔）
- [ ] R3-c verifier 完成词收紧：宽泛两字词（"完成"/"阶段"）改短语匹配（"已完成"/"已全部完成"），或仅当声称完成且本回合无任何 tool.exec 才触发
- [ ] R3-d 熔断前给确认通道：deny 计数达上限前，引擎检测到施工证据（文件写入/测试全绿）直接放行，不逼模型"继续"
