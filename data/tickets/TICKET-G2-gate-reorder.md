# TICKET-G2 收工闸时序重排 + 死锁安全阀

## 一、owner 设计裁决（原话锚点）

1. "台账放在回复之前。回复之前先处理台账，确认以后给出回复，回复结束代表结束。"
2. "结束就用 ready 来显示，和现在一样，只是台账在回复之前处理。"

语义目标：**回复发出 = 收工闸已通过 = 回合结束；ready 亮 = 账平事毕**。

## 二、现状与问题

现状：agent 生成最终回复 → 进 RESPONDING → 收工闸查账 → 不平则回注继续。问题：① 回复≠结束，用户看到"回复了还在 musing"；② auto 缺字段永不熔断（票 C 裁决）在 office 无人值守场景 = 无限空转烧 token（11:49 员工 musing 1m+ 实证）。

## 三、施工内容

### G2-1 时序重排（先账后复）

- 引擎在生成**最终回复之前**执行收工闸判定（现有 `_ledger_field_issues`、pending 回注、无账工作回合判定逻辑全部保留，只挪位置）：
  - 账不平（pending 项/缺字段/工作回合无账）→ 不进入回复，回注继续干活（用户看到的是 Working，不是"回了还在想"）
  - 账平 → 生成并发出最终回复 → 回合结束
- **纯聊天快速通道不动**：无工具调用且无台账的回合直接回复，不经闸。
- **TUI 显示逻辑零改动**：ready 出现即代表闸已通过（验收钉死）。
- 中断语义不动：ESC 中断保进度（票 E）照原链路工作。

### G2-2 死锁安全阀

- auto 缺字段 deny（现无上限）改为：连续 deny **3 次**后，回注指令降级为"将该 item update 写明卡点转 pending 交接/上报调度员，或补齐字段"；**第 5 次**强制放行 + ⚠️ 审计 `goal_gate.forced_release`（含 item 明细 + deny 次数）。
- 原则不变：不许装死收工；但给"真的卡住"一个留痕的出口。
- 普通模式原有 `_ledger_reinject_count < 2` 熔断语义不变。

### G2-3 测试语义迁移

- 现有 goal_gate 套件（test_goal_gate.py 13 + test_ticket_c_ledger_gate.py 14）断言的是"回复后回注"旧时序——按新时序重写断言，每条改动在 commit message/汇报中说明"语义迁移"而非"删测试"。
- 新增测试：先账后复（账不平无回复发出）、纯聊天快速通道、ready=闸过、安全阀 3 次降级/5 次强制放行、中断不受影响、auto off 对照组。
