# TICKET-AUTO-E2：ESC 随时硬中断——运行中命令可杀

> 立案：2026-08-10 · owner 实测 AUTO-E 时发现：execute_terminal 运行期间按 ESC 无反应
> 根因（已代码核实）：中断事件只在工具缝隙检查（tool_runner.py:339），单个工具运行期间阻塞等待
>   （execute_terminal 最长 120s），期间无人看中断事件。
> owner 原话定义："任何时候我按 ESC，它立马中断当前命令，完全中断当前执行，同时记得执行到哪个地步。"
> 分支：feat/ticket-auto-e2（自最新 main 切出）
> 纪律：branch 施工、五查汇报、未终审不 merge 不 push

---

## 一、施工内容

### E2-1. execute_terminal 改为可中断执行

- 执行层从"阻塞等返回"改为 **Popen（建议独立进程组）+ 轮询**：进程运行期间周期性检查 `_interrupt_event`；
- 事件一旦 set → **立即 terminate 进程组**（注意杀整组，防止子进程的子进程成孤儿；先 TERM，超时后 KILL）；
- 返回结果标注"⛔ 已被用户中断（ESC）"，已产生的部分 stdout/stderr 一并返回（现场证据不丢）；
- 事件总线照常留痕（cancelled (interrupt)）。

### E2-2. 中断后链路复用 E-1

- 中断后进度照常落盘（E-1 基建：checkpoints/messages/台账/save_session_to_disk），用户说"继续"能接上；
- 中断点语义：LLM 看到的工具结果是"被用户中断"，它应正常收束当前回合（不要重试同一命令——被用户拍停的命令自动重跑是事故）。

### E2-3. 中断响应时延指标

- ESC → 子进程死亡 ≤ 2 秒（轮询间隔建议 100-200ms）；
- 测试钉死：起一条 `sleep 30`，0.5s 后 set 中断事件，断言进程在 2s 内死亡且返回结果含中断标注。

### E2-4. 其他长超时工具评估

- spawn_worker（310s）等同理评估：若改动小则一并做，改动大则本票只记结论、另开票——不硬塞。

## 二、验收（终审口径）

1. `sleep 30` 运行中触发中断 → 2s 内进程死亡、结果含"已被用户中断"、事件留痕；
2. 中断后说"继续"→ session 进度完整（复用 E-1 测试范式）；
3. 中断的命令**不被自动重试**（断言中断后引擎不再发起同一 execute_terminal）；
4. 正常执行路径零变化：命令正常跑完时行为与现状一致；
5. ESC 三态语义不破（AUTO-E 前端测试全过）；
6. 全量 pytest（基线 1688/2）零回归；真实库 md5 闸门照旧。
