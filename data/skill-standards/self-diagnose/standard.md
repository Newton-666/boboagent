# Self-Diagnose Standard v1

> keywords: 开发, 改代码, 修复, bug, debug, 测试, 报错, 异常, 验证, 开发任务
> excludes: （无——这是通用开发纪律，任何代码任务适用）
> 价值: 任何代码任务（开发/改代码/测试/验证）命中 → 约束实弹验证+日志诊断+证据汇报（只约束动作，不约束表达）
> Bobo 在做任何代码任务时必须遵守本文档。本文档是硬约束，不是建议。
> 本 skill 只约束动作（实弹验证 / 日志诊断 / 证据汇报），不约束表达方式——怎么说都行，怎么做有纪律。

**工作流（三条纪律，硬约束）**：
1. **实弹验证**：核心链路改动（LLM 调用 / 事件流 / 数据写入）→ 改完必须自己发起一次真实调用验证（不是只看测试绿——单测是假环境，实弹才是真相；测试绿但实弹炸，等于没验证）
2. **日志诊断**：测试绿但行为怪 → 看 data/logs/bobo.log（或对应运行日志）→ 复现 → 最小化 → 根因（错误信息 / 日志 / 调用链逐层定位，不猜不改——禁止"我觉得是 X"直接动手）
3. **证据汇报**：附原始日志路径 / 测试输出文件路径，数字与日志逐字一致（禁止转述数字——转述 = 编造风险；汇报里的每个数字必须能指着日志原话复述）

**八步调试法**（遇 bug 时按序执行，不可跳步）：
1. 看现象（错误信息 / 复现步骤，先记录再动手）
2. 查日志（找事件 / 异常 / 线程线索，日志里有答案时禁止瞎猜）
3. 找可疑点（异步 / 并发 / 共享状态——症状与根因之间往往隔着时序）
4. 看调用链（参数构造——从调用方到被调用方逐层核对传参）
5. 定位根因（找机制非修表象——修完能解释"为什么是这里"）
6. 最小修复（不扩大改动面——改 bug 就是改 bug，不顺手重构）
7. 实弹验证（直接调一次确认——核心链路改动必须真实跑一遍）
8. 回归 + 守卫 + 提交（全量测试 + 专项守卫确认 + 收工汇报带证据）

**设计哲学**：测试全绿只是底线，不是证据。深层问题（400、广播缺口）往往在测试绿之后才暴露——所以核心链路改动必须实弹验证、行为怪必须先查日志、汇报必须附原始证据。这三条做到了，才叫"完成"。

## 约束

### 动作约束（违反任一条 = 不合格）

- ❌ 核心链路改动（LLM 调用 / 事件流 / 数据写入）只看单测绿就声称完成——必须实弹跑一次
- ❌ 行为异常时不查日志直接改代码——先复现、再最小化、再定位，禁止猜改
- ❌ 汇报数字不附原始日志路径或测试输出路径——数字必须可复现
- ❌ 测试绿就把深层问题（400 / 广播缺口 / 时序竞态）当不存在——测试绿 ≠ 真相，实弹才是
- ❌ 编造验证结果——实弹跑不动就如实说跑不动，禁止用"应该没问题"代替
