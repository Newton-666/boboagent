# Code Fix Standard v1

> keywords: bug, 修复, 报错, error, fix, debug, 崩溃, crash, 改代码, 修改, 出问题, 不工作, 失败, failed, broken, traceback, stack trace, panic, exception, 异常, 改一下, 修一下
> excludes: 样式, 配色, 设计, 布局, UI, 界面, 前端, 网页, 落地页, 美观, 好看, 文档, 文案, 图片, 视频
> requires: git-workflow
> 价值: 用户报 bug/要改代码时命中 → 约束先读后改+根因修复+验证证据（UI/文档类话题不注入）
> Bobo 在做任何代码修复/调试任务时必须遵守本文档。本文件是硬约束，不是建议。
>
> **工作流（必须遵守，不可跳过）**：
> 1. 错误信息定位 → grep_code 搜索错误关键词 + 堆栈中的文件名
> 2. 读上下文 → read_local_file 读问题文件和上下游调用方
> 3. 确认根因 → 区分症状和根因，用一句话描述"哪里、为什么"
> 4. 精确修复 → edit_file 替换，改动范围不超出问题函数
> 5. 验证 → run_tests 或 execute_terminal 跑测试，grep 确认无同类问题
> 禁止跳过任何步骤。禁止未读文件直接编辑。禁止不验证就声称"已修复"。
>
> **设计哲学**：修改代码之前，你的理解必须达到能给同事解释清楚问题根因的程度。不是"改了就不报错了"——而是"这个问题是因为 X，改 Y 可以解决，不会影响 Z"。

## 约束

### 绝对禁止（违反任一条 = 不合格）

- ❌ 未调用 `read_local_file` 或 `grep_code` 读取/定位文件内容，就直接调用 `edit_file`
- ❌ 只看报错行不看上下文（调用方、被调用方、变量来源）
- ❌ 不验证就声称"已修复"、"已完成"——每次声称修复后必须提供验证证据（测试输出、文件路径、返回值）
- ❌ 跳过 Phase 5.5 验证五查就交付——测试全绿只是底线，不是证据
- ❌ 修复时顺手重构无关代码——改 bug 就是改 bug，不改命名、不改结构、不改格式
- ❌ 修改 ≥ 3 个文件时一次性全部改完——先改核心文件，验证通过后再改其余文件
- ❌ 修复后又产生新的报错但不处理——修复范围是"问题解决"，不是"原来的报错消失但引入新问题"
- ❌ 编造执行结果——工具调用失败了就说失败了，诚实报告阻塞比伪造输出好
- ❌ **测试/直测/验证时读写真实数据文件**——knowledge_base、会话记录、用户笔记、配置文件等一律视为用户财产。验证任何带写操作的函数前，必须先把存储路径隔离到 tmp_path / monkeypatch / 临时副本，确认隔离生效后再调用。对别人的项目同理：跑对方代码前先确认它不会写坏对方的数据（2026-07-27 事故：直测 `_save()` 未隔离，覆盖 113 条真实记忆，靠 APFS 快照才救回）

### 必须遵守

- 每个 `edit_file` 调用之前，历史中必须能看到对同一文件调用过 `read_local_file` 或 `grep_code`
- 报错信息中的每个文件名和行号都必须用 `read_local_file` 实际查看
- 修复范围：一次 `edit_file` 只改一个逻辑问题。多个独立 bug → 多次 `edit_file`
- `old_string` 必须是文件中**实际存在的文本**（逐字符匹配，包括缩进和空格）——如果不确定，再读一次文件确认
- 直测任何带写操作的函数之前，先确认它的存储目标已被隔离到临时路径（`tmp_path` / `monkeypatch` / 副本），并打印一次实际路径自证；隔离没生效就调用 = 违规

## 工作流状态机

### Phase 1: 定位（LOCATE）

**目标**：把报错信息转化为文件路径 + 行号。

**步骤**：
1. 从报错信息或用户描述中提取关键词（函数名、类名、错误类型、文件名）
2. 用 `grep_code` 搜索这些关键词，定位到具体文件和行号
3. **如果报错信息中已经包含文件名和行号**，直接进入 Phase 2——不需要再 grep
4. **如果 grep 无结果**，换关键词或放宽正则，但不要原样重试超过 2 次
5. 如果报错涉及多个文件，先确定调用链：谁调了谁、谁抛了异常

**输出**：一个或多个 `文件:行号` + 错误类型。

### Phase 2: 读上下文（READ）

**目标**：理解问题的完整上下文，而不是只看报错的那一行。

**步骤**：
1. 用 `read_local_file` 读取报错文件，关注：
   - 报错行所在的函数/方法
   - 函数签名（参数类型、返回值）
   - 关键变量的定义和赋值来源
   - 调用链：谁调用了这个函数，传了什么参数
2. 如果问题涉及跨文件调用，**必须读被调用方的代码**——不能只看调用方就下结论
3. 如果文件超过 200 行，用 offset+limit 分页读关键部分（报错函数 + 前后各一个函数）

**输出**：对问题函数的作用、输入输出、调用关系的完整理解。此时你应该能用一句话解释根因。

### Phase 3: 确认根因（DIAGNOSE）

**目标**：区分症状和根因。报错的地方不一定是问题根源。

**步骤**：
1. 追问自己：这个变量为什么是这个值？这个状态为什么是这个状态？
2. 如果根因在上游（调用方传了错误的参数、配置没有加载、外部依赖没有初始化），**先修上游**
3. 如果根因是逻辑错误（条件写反了、off-by-one、类型不对），直接修当前文件

**输出**：一句话描述根因，格式为"问题出在 [文件:行号]，原因是 [根因]，修复方式是 [方案]"。

### Phase 4: 精确修复（FIX）

**目标**：最小改动解决问题，不动无关代码。

**步骤**：
1. 用 `edit_file` 做精确字符串替换
2. `old_string` 必须包含足够上下文使其唯一（前后 1-2 行），且逐字符匹配文件内容
3. 改动范围 ≤ 出问题的函数/方法——不跨函数重构
4. 如果涉及 ≥ 3 个文件，分批修复：
   - 第一批：核心文件（问题的直接位置）
   - 验证通过后
   - 第二批：其余文件
5. 修复完成后，用 `run_tests` 或 `execute_terminal` 执行相关测试

**输出**：文件路径 + 具体改动（改了哪个函数、哪几行、为什么这样改）。

### Phase 5: 验证（VERIFY）

**目标**：确认问题已解决，且没有引入新问题。

**心态**：你的任务不是确认"能用了"，是找出"哪里还不能用"。
测试全绿只是底线，不是证据——2026-07-27 三个 bug 全部发生在测试全绿背景下。

**步骤**：
1. 跑项目测试：`run_tests` 或 `execute_terminal("python3 -m pytest tests/ -x -q")`
2. 测试失败 → 回到 Phase 2，读失败详情，修复，再测
3. 用 `grep_code` 搜索同类模式（同样的错误模式可能出现在多个地方）
4. 如果有同类问题，一并修复 → 再测
5. 最后确认：原来的错误不再出现，且没有新的测试失败

**输出**：测试结果（pass/fail 数量）+ 是否发现同类问题。

### Phase 5.5: 验证五查（声称"完成"前的强制动作，2026-07-27 新增）

**测试绿 ≠ 没问题。完成汇报前必须逐项自查并附证据：**

1. **编译底线**：改动过 `.py` 文件 → 跑 `python3 -m py_compile <文件>`。
   语法错误交付是最低级的失守（当日案例：server.py 多一行 else 直接起不来）。
2. **通路检查**：你改的东西经过几层？走到**执行链最后一环**确认真的生效。
   注入点 ≠ 执行点、缓存点 ≠ 数据源、标记 ≠ 全文。
   （当日案例：工具桩传进 Engine 但执行器绕过它直接 import 真函数——
   只测"属性传到了"没测"末端用了它"。）
3. **真实运行**：用真实输入把改动点跑一遍，贴实际输出。
   不许只跑单测——单测的 mock 不会替你发现判空写反
   （当日案例：`_briefing()` 单测全绿，`repr()` 一跑永远返回 ''）。
4. **环境一致性**：bobo 实际加载的是不是刚改的这份代码？
   检查第二副本：site-packages 快照、dist/ 构建产物、~/.bobo 残留。
   （当日案例：.venv 里 7 月 26 日的 pip 快照让所有新交付隐形。）
5. **证据式自报**：完成汇报必须附证据——编译结果、测试输出、真实运行输出、
   改动文件清单。**禁止裸奔的"已完成""修好了"。**
   没找到问题就报告"我查过 X/Y/Z 没发现问题"，不许直接说"没问题"。

**输出**：五项逐项结论 + 证据。任何一项没过 → 回到对应 Phase，不许交付。

## 决策树：收到报错信息后的第一反应

```
报错信息包含文件名和行号？
  ├─ 是 → Phase 2（直接读文件，不 grep）
  └─ 否 → Phase 1（grep 定位）

报错涉及多个文件？
  ├─ 是 → Phase 2 时全部读，确定调用链
  └─ 否 → Phase 2 只读一个文件

修复涉及 ≥ 3 个文件？
  ├─ 是 → 分批修复，先核心后其余
  └─ 否 → 一次性修复

测试失败？
  ├─ 是 → 回到 Phase 2（不是 Phase 1——已经知道文件了）
  └─ 否 → 完成，汇报结果
```

## 验收

- [ ] 每个 `edit_file` 之前都调过 `read_local_file` 或 `grep_code` 查看同一文件
- [ ] 读过了上下游代码，不只是报错行
- [ ] 能一句话解释根因（不是症状）
- [ ] 改动范围在问题函数内，没有顺手重构
- [ ] 修复后的代码通过了相关测试
- [ ] grep 确认无同类遗漏问题
- [ ] 修复结果提供了具体证据（测试输出、文件路径）

## 工具速查与产出物形态（2026-08-07 由 E2-④ 身份段迁入，搬家不烧书）

**产出物形态**：
- 做网页/前端项目直接写 HTML/CSS/JS 文件——不要用 Python 脚本生成 HTML。写出的代码就是最终产品，不要绕一层中间脚本。
- 创建新文件 → file_operation（action="write"）+ auto-run（写完自动运行）
- 代码变更尽量用 ```diff 格式展示（+ 新增行，- 删除行）

**工具速查**（GUIDANCE Quick reference 已覆盖的 grep/edit/读/列表/跑测试/写笔记不再重复）：
- 项目结构 → index_project（首次接触项目时建立代码索引，后续无需重复搜索结构）
- 搜索信息 → web_search / search_obsidian / cross_search
- 短内容写入（约 40000 字符以内）→ write_obsidian（安全、有自动备份）
- 长内容写入（超过 40000 字符）→ execute_terminal 的 cat / echo 命令（无大小限制）
- 时间/日期 → get_current_time
- 普通聊天 → 直接回答
