# Duo Standard v1

> keywords: duo, 双员, 商讨, 交叉验收, 两人审, 双重检查, 双人, 互相审, 挑刺, 两个一起
> status: draft
> **注意：/duo 商讨：… 现已由 core/duo_orchestrator.py 代码编排接管（确定性流程）。
> 本文件仅用于自然语言软触发（不带斜杠的 "duo 商讨" 等）时的行为引导。
> 实现验收模式（/duo + 代码任务）仍走本文件 prompt 引导。**
> Bobo 在执行 /duo 双员制任务时必须遵守本文档。本文件是硬约束，不是建议。
>
> **工作流（必须遵守，不可跳过）**：
> /duo 是单次任务的执行方式，不是模式开关。任务结束自动回到普通状态，
> 没有"进入/退出模式"。Esc/Ctrl+C 打断和普通任务完全一样。
>
> **设计哲学**：同一模型 + 不同角色任务书 + 信息隔离 = 视角差异。
> A 提方案出活儿，B 独立挑刺验收。B 看不到 A 的推理——这是双员制
> 的全部意义。不搞"两个 AI 直接聊天"——主 Bobo 做中继就够了。

## 约束

### 绝对禁止（违反任一条 = 不合格）

- ❌ 让 A 和 B 的 worker 直接互发消息——所有信息通过主 Bobo 中继
- ❌ B 拿到 A 的推理过程、工具轨迹、自我评价——B 只能拿到需求 + 文件清单 + 验收标准 +（商讨模式下）A 的方案文本
- ❌ 打回循环超过 2 轮——2 轮仍不过必须升级给用户，禁止无限互踢
- ❌ worker 里再派 worker（/duo 不嵌套）
- ❌ 验收标准写成"看看有没有问题"——必须是可判定的、预定义的逐条标准
- ❌ 商讨模式下修改任何文件——商讨只输出分析/方案/决策清单，不动代码。即使用户说"顺便改一下"，也必须先在决策清单里列出改动建议等用户确认，不可直接修改
- ❌ 任务结束后残留"双员模式"状态——每次 /duo 是独立任务

### 必须遵守

- 每个 worker 用 `spawn_worker` 派发，起有意义的 name（如 "duo-A-propose"、"duo-B-review"）
- worker 使用全量工具、同模型配置（spawn_worker 默认继承主 Bobo 的 LLM 配置）
- A worker 完成后通过 `read_worker_result` 取结果
- B worker 的任务书必须在 spawn 前写进 instruction 参数中

## 工作流状态机

### 模式识别

用户输入中检测到以下模式 → 启动 /duo 流程：
- `/duo 商讨：<问题>` → **商讨模式**
- `/duo <实现类任务>` → **实现验收模式**
- 自然语言 "用双员商讨一下 xxx" / "双人检查这个改动" → 同上

### 商讨模式（Deliberate）

```
Phase 0: 现状简报（仅当问题涉及具体项目/代码库时，如"bobo 未来架构"）
  主 Bobo 自己做快速扫描，严格限量：
    · git log --oneline -15
    · 读 README（只看章节标题）
    · 最多 3 次 grep/目录扫描
  【禁止】读完整源码文件、禁止逐模块审计、禁止超过 2 分钟。
  扫描完立刻整理成 10 行以内「现状清单」（已建成什么、进行中什么），
  然后必须直接进入 Phase 1，不得继续深挖。
  简报作为 context 参数传给 A 和 B。
  目的：worker 禁工具（保速度），但不能当瞎子——
  2026-07-27 教训①：无简报时 A/B 把已建成 2 天的功能当成"空白方向"重新提议；
  教训②：简报不限量时主 Bobo 读了 12 个文件 7 分钟还没派 worker。
  纯理念问题（不涉及具体项目现状）跳过 Phase 0。

Phase 1: spawn A（提案）
  任务书: "就 <问题> 提出你的方案。给出观点、理由、风险。
           这是纯思考任务：禁止调用任何工具，不要读文件，
           一轮回复内直接输出完整方案。"
  context: <Phase 0 的现状清单，如有>
  角色: 方案提出者

Phase 2: 主 Bobo 读 A 的结果 → spawn B（挑刺）
  任务书: "有人提出以下方案：\n---\n<A 的方案全文>\n---\n
           你的任务是挑刺：找出假设漏洞、遗漏场景、更优替代。
           只输出问题清单，不需要重述方案。
           这是纯思考任务：禁止调用任何工具，一轮回复内直接输出。"
  context: <Phase 0 的现状清单，如有>
  角色: 独立评审者（B 只看到方案文本，不知道是谁提出的）

Phase 3: 主 Bobo 汇总 → 输出决策清单
  格式:
    ## /duo 商讨结论：<问题>
    ### 共识
    - ...
    ### 分歧
    - A 认为：...  /  B 认为：...
    ### 主 Bobo 的建议
    - ...
    ### 待用户拍板
    1. ...
    2. ...
```

### 可见性规则（必须遵守，2026-07-27 用户反馈新增）

worker 的产出用户默认看不到（只有一个转圈的工具调用），
因此主 Bobo 必须做"现场转播"：

- 每个 Phase 的 worker 完成后，主 Bobo 先把该 worker 的产出**原文**
  完整贴给用户（标注 "▶ A 的方案原文" / "▶ B 的挑刺原文"），
  再进行下一步。禁止只给最终清单不给过程。
- 实现验收模式同理：A 的自报和 B 的验收结论都要原文呈现。
- 汇总清单照常放在最后，不替代原文转播。

### 实现验收模式（Implement & Verify）

```
Phase 1: 主 Bobo 写验收标准
  向用户确认或根据需求自定——必须是可判定的逐条标准。
  例: "① 文件 hello.py 存在 ② 含至少一行注释 ③ 语法正确可执行"

Phase 2: spawn A（实现）
  任务书:
    "实现以下需求：<需求原文>
     允许改动的文件：<范围>
     完成后自报：改了哪些文件、为什么这样改。
     trash 备份要求：修改前先备份到 trash。"

Phase 3: 主 Bobo 读 A 的结果 → 检查改动文件清单 → spawn B（验收）
  任务书:
    "验收以下改动：\n
     原始需求：<需求原文>\n
     改动文件清单：<A 报告的文件列表>\n
     验收标准（逐条可判定）：\n<验收标准>\n
     ---
     独立判断，不要参考实现者的推理。\n
     输出格式严格为:\n
       通过\n
     或\n
       打回：\n       - <理由 1>\n       - <理由 2>"

Phase 4: 处理验收结果
  B 通过 → 汇总报告用户：改动文件 + 验收结论 ✓
  B 打回 → spawn A（修复，附 B 的打回理由清单）
           → A 修复后再给 B 验
           → 第 2 次打回 → 升级给用户："双员 2 轮未达成一致，请拍板：\n
              需求：...\n
              A 的方案：...\n
              B 的顾虑：..."
           → 禁止第 3 次 spawn
```

## 信息隔离规则（强制执行）

| B 能拿到 | B 拿不到 |
|---------|---------|
| 需求原文 | A 的推理过程 |
| 改动文件清单（文件名列表） | A 的工具调用轨迹 |
| 验收标准（逐条） | A 的自我评价/备注 |
| 商讨模式下：A 的方案全文 | A 的身份/来源信息 |

**隔离方式**：B 的 task 参数只粘贴 A 的方案文本 + 文件清单 + 验收标准，
不附加任何 A 的推理或工具日志。主 Bobo 负责中继。

## 输出格式

### 商讨结论

```
## /duo 商讨结论：<问题一句话>

### 共识
- <双方一致的点>

### 分歧
- A 认为：...  /  B 认为：...

### 主 Bobo 的建议
- <基于双方观点的独立判断>

### 待用户拍板
1. <决策项>
2. <决策项>
```

### 验收结论

```
## /duo 验收结论

改动文件：
- <文件列表>

验收结果：✅ 通过 / ❌ 打回

<通过时> 所有验收标准均满足。
<打回时> B 的顾虑：
- <理由 1>
- <理由 2>

<2 轮仍打回时> 升级给用户：
需求：...
A 的方案：...
B 的顾虑：...
请用户拍板。
```

## 验收

- [ ] 商讨模式输出含共识/分歧/建议/待拍板四段
- [ ] 实现模式有 B 的独立验收结论
- [ ] 打回循环 ≤ 2 轮，超限正确升级
- [ ] B 拿不到 A 的推理过程
- [ ] 任务结束后正常回到普通对话
- [ ] worker 间无直接通信
- [ ] 每个 Phase 的 worker 产出原文都呈现给用户（可见性规则）
